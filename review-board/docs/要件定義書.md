## 第0項：全軸ベースライン以上宣言 ＋ 重点軸宣言

> 共通方針の品質方針宣言に従い、本子が継承する品質の床と、突出させる軸を明記する。

### 継承宣言（全軸ベースライン以上＝床）

本アプリは共通の設計方針 を継承し、品質指標すべてを **ベースライン以上（全軸基準達成）** に保つ。
すなわち、安定性・信頼性／保守性・拡張性／性能・UX は、本書で S を取らない軸であっても
共通の品質指標群 MUST 要件を満たす（付録A ベースライン判定表で確認する）。

### 重点軸宣言：セキュリティ・認可 を S へ

本アプリの目玉（差別化）は「**他者の成果物・レビューを安心して見せ合える、信頼できる成長記録の場**」である。
クローズド・コミュニティ／複数ロール（受講生・講師）／他人の成果物閲覧という構造上、
**認可の堅牢さこそが本アプリの品質的突出点**である。よって品質指標のうち **セキュリティ・認可 を S** とする。

**重点基準（測定可能な形・付録A 重点判定表に転記）：**
- 認可テストが全エンドポイントを網羅し、IDOR（他人/他cohortの資源アクセス）が自動テストで 100% 阻止される
- 依存脆弱性スキャン（`npm audit` / OWASP dependency-check 等）を CI に常設し、High/Critical 0 件を維持
- 主要な認可境界（誰が・何に・何の権限を持つか）を脅威モデリング表として文書化・保持する
- 監査ログで「誰が・いつ・誰の資源に・何をしたか」を追跡できる

### 床を割らない約束（Sの代償に A 未満へ落とさない軸）

セキュリティ・認可を S へ引き上げる代償として、以下を A 未満に落とさないことを約束する：
- **性能・UX**：認可チェックの多層化で体感速度を犠牲にしない（主要操作の API 応答 P95 をP-1 基準内に保つ）
- **保守性**：認可ロジックを散在させず、ロールベースで一元化する（M-3 責任分離を維持）
- **安定性**：認可失敗時も graceful に 403/404 を返し、全体を止めない（1-1 障害耐性を維持）

## 1. プロジェクト概要

### 1-1. 背景・課題

エンジニアスクールでは、講師が全受講生の成果物を十分にレビューしきれない。一方で受講生は
「レビューされる経験」も「他人のコードを読んでレビューする経験」も不足しがちで、学習が孤独になりやすい。

そこで、**受講生同士が互いの成果物をレビューし合い、その積み重ねが個人の「成長の証跡」として
可視化される**プラットフォームを開発する。レビューは成長記録に積み上がる栄養であり、主役は
「受講生一人ひとりの成長記録ページ」である。

### 1-2. 目的（学習到達点）

> **学習姿勢:** 「習うより慣れろ → マスターしろ」（sns-board より継承）。
> Phase 1〜2 でまず動くものを作り、Phase 3 以降で「なぜこの認可設計か」「IDOR の芽はどこか」を
> 自分の言葉で説明できる水準まで深掘る。

#### 学習対象（到達点の具体）

- **ロールベース認可（RBAC）**を設計・実装する（受講生／講師の権限差）
- **IDOR 対策**を体系的に学ぶ（他人のレビュー・他 cohort の記録へのアクセス遮断）
- **クローズドなアクセス制御**（ログイン必須・所属 cohort 内のみ閲覧）を実装する
- 認証（メール＋パスワード）と JWT in HttpOnly Cookie（SEC-7 継承）を実装する
- UGC（レビュー本文）の XSS / バリデーション対策を実装する
- 「成長の可視化」のためのデータ集計（もらった/したレビュー・実績スコア）を設計する

### 1-3. 対象ユーザー

- **クローズド**：スクール内メンバー限定（招待制／管理者がアカウント発行。誰でも登録できる仕様にはしない）
- ロール：**受講生 / 講師**（将来 admin / moderator を追加可能な設計）
- 所属：**cohort（期・コース・クラス）**に属する。MVP では全員が 1 つの cohort でも動く
- 想定利用者数：1 cohort あたり 5〜30 名

### 1-4. 利用環境

- PC ブラウザ：Chrome / Edge / Safari 最新版
- モバイルブラウザ：iOS Safari / Android Chrome 最新版（レスポンシブ対応）
- ネイティブアプリは対象外

### 1-5. 差別化ポイント

| 項目 | 一般的なレビューSNS | review-board |
|---|---|---|
| 主役 | 投稿とレビューのやり取り | **個人の成長記録ページ（証跡）** |
| レビューする側の扱い | 評価されない | **「したレビュー」も実績化**（過疎化を防ぐ動機設計） |
| レビューの質 | 自由記述（空疎になりがち） | **品質指標に沿った観点枠で構造化**（建設的・レビューする側の学習が品質思想と連動） |
| 講師の関与 | なし／一律 | **講師レビューを特別表示＋成果物の最終評価・承認**（合格バッジ＝最高の証跡） |
| 公開範囲 | 公開 | **クローズド（cohort 内）**（採用向けの作り込みは対象外） |

### 1-6. 指導理念・行動指針（講師の言葉）

> 本プロジェクトはエンジニアスクールの学習環境で開発される。以下は講師から受け継ぐ行動指針であり、
> 本アプリの設計思想（成長記録が主役・講師の関与）の根拠でもある。単なる標語ではなく、各理念を
> 具体的な機能・品質軸に結びつけて運用する。

- **継続は力なり** — 講師の言葉で継続できることが何より大事。学習は一度の成果ではなく積み重ねで伸びる。
  → 成長記録ページ（`F-PROF-01`〜`F-PROF-04`）で継続を可視化し、「続けたくなる」動機を設計する。
- **やったことがないことをするのが、エンジニアの仕事** — 未知への挑戦そのものが価値であり、学びの源泉。
  → 新技術の先行採用（Java 25 LTS・§2-3）や、未経験の認可設計（重点軸：RBAC / IDOR 対策）に踏み込む姿勢を後押しする。
- **スクールを全力で活用し、講師を使い倒す** — スクールを使っているのだから、講師を最大限活用すること。
  → 講師レビューの特別表示（`F-REV-02`）・講師による成果物の最終評価／承認（`F-EVAL-01`、合格バッジ＝最高の証跡）として、講師の関与を仕組みに組み込む。

## 2. 前提条件と制約

### 2-1. 前提

- 学習プロジェクトであり、当面は実運用しない（将来の実運用は可能性として残す）
- 「スクール内で完結する成長記録」が主目的。外部公開・SEO・採用向けポートフォリオは対象外
- AWS 無料枠の範囲内で運用する（task-board / sns-board の運用ポリシーを継承）

### 2-2. 制約

- **コスト**：月 $0.50 以下に抑える（修練城の AWS Budget 防御層に従う）
- **セキュリティ**：機密情報の平文ハードコード絶対禁止（SEC-9・task-board 2026-05-07 事故の継承）
- **スコープ**：現フェーズ（学習）ではインフラ簡素化（CloudFront / WAF 等は対象外。簡素化の事実として明記）

> **本実装移行時の再検討（横断原則）：** 本書および各設計ドキュメントで「学習目的のため対象外／
> 簡素化」と記した不採用・簡素化は、**恒久的な排除ではなく現フェーズの判断**である。§2-1
> 「将来の実運用は可能性として残す」のとおり、**本実装（実運用）へ移行する場合は各項目を再検討**する
> （例：CloudFront / WAF、カバレッジゲート、E2E ツールの本格化）。

### 2-3. 技術スタック（確定事項）

| 層 | 採用技術 |
|---|---|
| バックエンド | **Java 25**（LTS）＋ Spring Boot ＋ Gradle |
| フロントエンド | **React** ＋ Vite（＋ Tailwind CSS を想定） |
| データベース | PostgreSQL（Docker） |

> **family との差分（明記）：** task-board / CLAUDE.md は Java 21 を基準としているが、本アプリは
> 学習として **Java 25（LTS）** をベースに採用する。Spring Boot の採用バージョンが Java 25 を
> サポートすることを技術スタック.md 起こし時に確認する（M-14：Toolchain と実行ランタイムの整合）。

## 3. 機能要件

### 3-1. Phase 別スコープ

#### Phase 1（MVP）— 「投稿 → レビュー → 成長記録」の最小一周

- **認証・ロール**
  - `F-AUTH-01` メール＋パスワードでログイン（JWT in HttpOnly Cookie）
  - `F-AUTH-02` ロール（受講生／講師）を持つ。アカウントは管理者が発行（招待制）
  - `F-AUTH-03` 全ページがログイン必須。未ログインはアクセス不可
- **投稿（成果物）**
  - `F-POST-01` 成果物を投稿する：**URL ＋ スクショ ＋ 説明文 ＋ タイトル**（対象を問わず1種類の形式）
  - `F-POST-02` 自分の投稿を編集・論理削除する（S-4）
  - `F-POST-03` 同じ cohort の投稿一覧を見る（ページネーション・P-2）
- **レビュー**
  - `F-REV-01` 他人の投稿にレビューを書く：**品質指標に対応した観点枠**で構造化
    - 「✅ 良かった点（自由）」＋「観点別コメント（任意・各軸）：①動作・正しさ ②可読性・保守性 ③セキュリティ ④性能・UX」＋「💡 もっと良くなる点（自由）」
    - 観点は任意入力（初心者が全軸埋められなくてもよい）。「良かった点／改善点」の自由記述は必須
  - `F-REV-02` 講師のレビューは `reviewer.role` で特別表示（バッジ等）
  - `F-REV-03` 投稿者がレビューに「ありがとう」を返す → レビュアーの実績に反映
  - `F-EVAL-01` **講師による最終評価・承認**（講師ロールのみ）：成果物に対し「承認（合格）／差し戻し」＋評価コメントを付与
    - 承認結果は成長記録ページに「合格バッジ」として表示（最高の証跡）。差し戻しは再投稿を促す
    - 1 投稿につき最新の講師評価を 1 件保持（履歴は残す。S-4 論理削除・履歴保持）
- **成長記録ページ（主役）**
  - `F-PROF-01` 投稿した成果物の履歴
  - `F-PROF-02` もらったレビュー一覧（講師レビューは強調）
  - `F-PROF-03` したレビューの実績（件数・もらった「ありがとう」数）
  - `F-PROF-04` 講師に承認された成果物の「合格バッジ」を表示（最高の証跡）

#### Phase 2 — 質を高める

- レビューへの返信（スレッド）、レビュー対象の絞り込み・検索
- 成長記録のビフォーアフター可視化（投稿の時系列）
- 通知（自分の投稿にレビューが付いた／ありがとうが付いた）

#### Phase 3 — 拡張（将来）

- **レビュー対象の多様化**：GitHub コード/PR への行コメント、学習記事、質問・詰まりごと
- **cohort の複数運用**：複数の期・コースを出し分け（MVP のテーブル設計で受けられるようにしておく）
- moderator ロール、AWS デプロイ

> **MVP で投稿対象を1種類（URL＋スクショ＋説明）に絞る理由：** コード・記事・デザインで
> レビュー UI と評価軸が全く異なる（行コメント／注釈／文章コメント）。最初から全部作ると中途半端になるため、
> 「URL を貼れば対象を問わず成立する自由コメント型」1種に絞り、行単位コメントや GitHub 連携は Phase 3 に回す。

### 3-2. ロールと権限（RBAC）— 重点軸の中核

| 操作 | 受講生 | 講師 | 未ログイン |
|---|---|---|---|
| ログイン | ✅ | ✅ | — |
| 同 cohort の投稿閲覧 | ✅ | ✅ | ❌ |
| 投稿の作成 | ✅ | ✅ | ❌ |
| **自分の**投稿の編集・削除 | ✅ | ✅ | ❌ |
| 他人の投稿の編集・削除 | ❌ | ❌ | ❌ |
| レビューの作成 | ✅ | ✅（特別表示） | ❌ |
| **自分の**レビューの編集・削除 | ✅ | ✅ | ❌ |
| **成果物の最終評価・承認**（合格／差し戻し） | ❌ | ✅ | ❌ |
| 他 cohort の資源の閲覧 | ❌ | ❌（将来 admin のみ） | ❌ |

> **最終評価・承認は講師ロール限定**の操作であり、重点軸（認可）の重点検証対象。受講生がこの操作を
> 呼べないこと（権限昇格・IDOR）を認可テストで必ず確認する。

> 権限はロールベースで一元判定する（SEC-4）。「誰のものか（所有者 / cohort 一致）」は
> バックエンドで必ず検証し、不一致は 404 を返す（SEC-2・SEC-3、IDOR 対策）。

## 4. 非機能要件（品質指標を継承して具体化）

> 全要件 ID は共通の品質指標群に対応する。ここでは本アプリ固有の数値・対象に具体化する。
> 重点軸（セキュリティ・認可）は付録A 重点判定表の上位指標で測る。

### 4-1. セキュリティ（★ 重点軸）

- SEC-1〜SEC-13 をすべて MUST として継承
- **`F-AUTH` `F-POST` `F-REV` `F-PROF` の全エンドポイントに認可テストを書く**（正常系＋他人/他cohort アクセスの拒否系）
- IDOR：URL のリソース ID 書き換えで他人のレビュー・投稿・成長記録に到達できないこと（自動テストで検証）
- 認証：JWT in HttpOnly Cookie（access 短命 + refresh DB rotation + reuse detection、SEC-7）
- 依存脆弱性スキャンを CI に常設（High/Critical 0 件維持）

### 4-2. 安定性・信頼性（A 維持）

- S-1〜S-8 を継承。論理削除（S-4）で成長記録の参照整合性・履歴を保つ
- 成長記録（もらった/したレビュー数・ありがとう数）の集計は非正規化カウンタ＋定期再計算でズレ補正（S-3）

### 4-3. 保守性・拡張性（A 維持）

- M-1〜M-15 を継承。Controller / Service / Repository の責任分離（M-3）
- `role` と `cohort` を最初からデータモデルに持つ（後付け回避）。複数 cohort 出し分けは Phase 3 だがテーブルは先に用意

### 4-4. 性能・UX（A 維持）

- P-1〜P-10 を継承。投稿一覧・成長記録はページネーション（P-2）、N+1 回避（P-3）
- スクショ画像は外部ストレージ（MinIO/S3）に保存し DB 肥大化を回避（P-10・SEC-8）

## 6. リスク・前提（R 形式）

| ID | リスク | 対策 |
|---|---|---|
| R-01 | レビュアーのインセンティブ不足で過疎化 | 「したレビュー」を実績化＋「ありがとう」返しで動機づけ（差別化ポイント） |

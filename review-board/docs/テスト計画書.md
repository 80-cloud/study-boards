## 1. 目的とスコープ

### 目的
review-board の品質指標（特に **重点軸＝認可**）を、測定可能なテストで担保する。要件定義書 §0 の
「IDOR が自動テストで 100% 阻止される」「認可テストが全エンドポイント網羅」を本書で具体化する。

### スコープ（Phase 1）
F-AUTH（認証・ロール）／F-POST（投稿）／F-REV（レビュー・ありがとう）／F-EVAL（講師評価）／
F-PROF（成長記録）の全エンドポイント。Phase 2/3 は §9 に予約。

---

## 2. テストレベル

| レベル | 対象 | 手段 |
|---|---|---|
| 単体（unit） | Service の業務ルール（自己レビュー禁止・カウンタ増減・is_latest 切替） | JUnit 5 / Mockito |
| 結合（integration） | Controller→Service→DB の認可・永続化 | `@SpringBootTest` + Testcontainers(PostgreSQL) |
| フロント単体 | コンポーネント・サニタイズ | Vitest + Testing Library |
| E2E / 疎通 | 主要フロー（ログイン→投稿→レビュー→評価→成長記録） | Chrome DevTools MCP（手動疎通・§8） |

---

## 3. テスト技法

- **ホワイトボックス**：分岐網羅（認可分岐＝ロール × 所有者 × cohort の組合せ）を Service/Controller で
- **ブラックボックス**：同値分割・境界値（タイトル 1/100/101 文字、スクショ 5MB 前後、URL 形式）
- 認可は「正常系より**拒否系**を厚く」書く（重点軸の本質は「呼べないこと」の保証）

## 6. ★ 認可テストマトリクス（重点軸の中核）

> 要件定義書 §3-2 RBAC 表・ER図 §9（cohort 境界）を全網羅する。**各エンドポイントについて以下のケースを必ず書く。**

| ケース | 条件 | 期待 |
|---|---|---|
| 正常 | 本人・同 cohort・正しいロール | 2xx |
| 未認証 | Cookie なし/失効 | **401** |
| ロール不足 | 受講生が講師専用操作（F-EVAL-01） | **403** |
| 他人の資源（編集系） | 他人の投稿/レビューを編集・削除 | **403 or 404** |
| 自己レビュー | 自分の投稿に自分でレビュー | **403** |
| 他 cohort の資源 | 他 cohort の投稿/レビュー/成長記録を閲覧・操作 | **404**（存在を漏らさず IDOR 遮断） |
| ID 書き換え | URL のリソース ID を他人/他 cohort に改変 | **404** |

### エンドポイント別チェックリスト（Phase 1）

| エンドポイント | 正常 | 401 | 403 | 404(他cohort/他人) |
|---|---|---|---|---|
| `POST /api/auth/login` | ✓ | — | — | — |
| `GET /api/posts`（一覧） | ✓ | ✓ | — | ✓（他 cohort が混ざらない） |
| `POST /api/posts` | ✓ | ✓ | — | — |
| `PUT /api/posts/:id`（編集） | ✓ | ✓ | ✓（他人） | ✓ |
| `DELETE /api/posts/:id` | ✓ | ✓ | ✓ | ✓ |
| `POST /api/posts/:id/reviews` | ✓ | ✓ | ✓（自己レビュー） | ✓（他 cohort 投稿） |
| `POST /api/reviews/:id/thanks` | ✓（投稿者のみ） | ✓ | ✓（投稿者以外） | ✓ |
| `POST /api/posts/:id/evaluation` | ✓（講師） | ✓ | ✓（受講生＝権限昇格） | ✓ |
| `GET /api/users/:id/profile` | ✓ | ✓ | — | ✓（他 cohort） |

> **権限昇格テスト**は最重要：受講生トークンで `POST /api/posts/:id/evaluation` を叩いて 403 を確認（要件定義書 §3-2 の重点検証対象）。

## 7. セキュリティテストの横展開

| 観点 | テスト内容 |
|---|---|
| IDOR | §6 のマトリクス（ID 書き換え・他 cohort）を全エンドポイントで自動化 |
| XSS | description/good/improvement/comment に `<script>` を入れ、表示時に DOMPurify で無害化されること |
| CSRF | 状態変更系（POST/PUT/DELETE）で対策が効くこと（SameSite Cookie + トークン） |
| 認証 | JWT 失効・refresh rotation・reuse detection（旧 refresh 再利用で全失効） |
| レート制限 | ログイン・投稿・レビュー作成で 429 が返ること |
| 依存脆弱性 | **OWASP dependency-check**（backend）/ **npm audit**（frontend）を CI 常設、High/Critical **0 件**維持（重点基準） |
| 監査ログ | 認可境界操作が `audit_logs` に記録されること |

## 8. E2E / 手動疎通確認

### 8-1. なぜ Chrome DevTools MCP か
現フェーズ（学習）では Playwright のフルセットアップは過剰。**Chrome DevTools MCP** で主要フローを手動疎通し、
コンソールエラー・ネットワーク応答・認可挙動（403/404）を目視確認する（sibling 同方針）。

> **再検討余地（要件定義書 §2-2 横断原則）：** これは恒久判断でなく現フェーズの判断。**本実装/実運用へ
> 移行する場合は、Playwright 等による E2E 自動化・CI 組み込みを再検討**する（カバレッジゲート §5 も同様）。

### 8-2. デプロイ前 手動ブラックボックス疎通チェックリスト（ローカル）
- [ ] 未ログインで保護ページ → S-01 にリダイレクト（401）
- [ ] 受講生ログイン → 投稿作成 → 一覧に出る（自 cohort のみ）
- [ ] 他人の投稿にレビュー（4軸フォーム）→ 投稿者に「ありがとう」される
- [ ] 受講生で評価 API を叩く → **403**（権限昇格不可）
- [ ] 講師ログイン → 承認 → 成長記録に**合格バッジ**点灯
- [ ] 別 cohort の投稿 URL を直接開く → **404**

### 8-3. 共通方針教訓との整合
- 「verify 前の『ゼロ』宣言禁止」：認可テスト緑＝既知ケースのみ。新ケースは随時マトリクスへ追記
- 検出した不具合は「N で発見・N で修正」のペアで報告

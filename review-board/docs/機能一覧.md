## Phase 1 機能詳細（MVP）

### F-AUTH-01: ログイン

**入力:**

| 項目 | 型 | 制約 |
|---|---|---|
| email | string | RFC 準拠、必須 |
| password | string | 8 文字以上、必須 |

**業務ルール:**

- 認証成功で **JWT を HttpOnly + Secure + SameSite Cookie** に発行（access 短命）。refresh は別途 DB rotation（母 SEC-7）
- 全ページがログイン必須（F-AUTH の前提）。未ログインは 401 → ログイン画面へ
- アカウントは事前に管理者が発行（招待制、F-AUTH-02）。サインアップ画面は持たない
- 失敗時はユーザー存在を漏らさない汎用エラー（列挙攻撃対策）

**API:** `POST /api/auth/login`

```
Request:  { "email": "...", "password": "..." }
Response: 200 (Set-Cookie: access/refresh) { "user": { "id", "displayName", "role", "cohortId" } }
        / 401 (認証失敗) / 400 (バリデーション)
```

### F-POST-01: 成果物投稿

**入力:**

| 項目 | 型 | 制約 |
|---|---|---|
| title | string | 1〜100 文字、必須 |
| description | string | 1〜5000 文字、必須（DOMPurify サニタイズ） |
| repoUrl | string | URL 形式、任意 |
| demoUrl | string | URL 形式、任意 |
| screenshot | file | JPEG/PNG/WebP、5MB、マジックバイト検証、S3 保存、任意 |
| techTags | string[] | 各タグ正規化・重複排除、最大 10 件 |
| reviewPoints | string | 「見てほしい点」自由記述、任意 |
| recruitStatus | enum | `OPEN`（レビュー募集中）/ `CLOSED` |

**業務ルール:**

- ログイン必須。作成者 = 投稿者、cohort は作成者の cohort を自動付与（クライアント指定を信用しない＝IDOR 対策）
- スクショは S3（ローカルは MinIO）に保存し、DB には参照キーのみ（母 P-10）
- 作品メタ情報（制作時間/学習期間/苦戦ポイント/対応状況など）は本機能では `post_meta` の任意キー値として受ける（個別カラム化しない。ER図で確定）

**API:** `POST /api/posts`（multipart）→ `201 { post }` / `401` / `400`

---

### F-POST-03: 投稿一覧（同 cohort）★S軸

**業務ルール:**

- ログイン必須。**自分の cohort の投稿のみ**を返す（他 cohort は返さない＝IDOR 遮断、母 SEC-2/3）
- カーソルベース pagination（offset 不採用、母 P-2）。N+1 回避（投稿者・タグを join/batch 取得、母 P-3）
- 並び順は新着降順（Phase 2 で F-FILTER-01 を追加）

**API:** `GET /api/posts?cursor=...&limit=20` → `200 { posts, nextCursor }` / `401`

---

### F-REV-01: レビュー投稿

**入力:**

| 項目 | 型 | 制約 |
|---|---|---|
| postId | number | 対象投稿。存在 + 同 cohort を検証 |
| good | string | 「✅ 良かった点」必須、1〜2000 文字 |
| improvement | string | 「💡 もっと良くなる点」必須、1〜2000 文字 |
| axisComments | object | 観点別（任意・各軸）：①動作・正しさ ②可読性・保守性 ③セキュリティ ④性能・UX |

**業務ルール:**

- ログイン必須。**自分の投稿にはレビュー不可**（自己レビュー禁止）。対象投稿が**他 cohort なら 404**（IDOR）
- 良かった点／改善点は必須、観点別は任意（初心者が全軸埋められなくてもよい・要件定義書 §3-1）
- 本文は保存時にプレーン保持し、表示時に DOMPurify でサニタイズ（XSS、母 SEC）
- 講師の投稿は `reviewer.role` で特別表示（F-REV-02）

**API:** `POST /api/posts/:postId/reviews` → `201 { review }` / `401` / `403`（自己レビュー）/ `404`（他cohort）/ `400`

---

### F-EVAL-01: 講師の最終評価・承認 ★S軸（権限昇格の重点検証対象）

**入力:**

| 項目 | 型 | 制約 |
|---|---|---|
| postId | number | 対象投稿（同 cohort） |
| result | enum | `APPROVED`（合格）/ `RETURNED`（差し戻し） |
| comment | string | 評価コメント、必須、1〜2000 文字 |

**業務ルール:**

- **講師ロール限定**。受講生がこの API を呼べないことを認可テストで必ず確認（権限昇格・要件定義書 §3-2）
- 1 投稿につき最新の講師評価を 1 件保持。過去は履歴として残す（論理削除・母 S-4）
- `APPROVED` は成長記録に**合格バッジ**として表示（F-PROF-04）。`RETURNED` は再投稿を促す
- 監査ログに記録（誰が・いつ・どの投稿に・どの結果、S基準）

**API:** `POST /api/posts/:postId/evaluation` → `201 { evaluation }` / `401` / `403`（講師でない）/ `404`

---

### F-PROF-01〜04: 成長記録ページ（主役）

**業務ルール:**

- ログイン必須。**同 cohort のメンバーの成長記録のみ閲覧可**（他 cohort は 404、IDOR）
- 集計（もらった/したレビュー数・ありがとう数）は**非正規化カウンタ + 定期再計算でズレ補正**（母 S-3）
- 表示内容：自己紹介・使用技術・投稿履歴（F-PROF-01）・もらったレビュー（講師は強調・F-PROF-02）・したレビュー実績（F-PROF-03）・合格バッジ（F-PROF-04）

**API:** `GET /api/users/:userId/profile` → `200 { profile }` / `401` / `404`（他cohort）

## 採否の判断記録（不採用機能とその理由）

> ブレスト一覧のうち、確定方針と矛盾する／スコープ外の機能を**明示的に不採用**とする。
> 「なぜ載せないか」を残すことで、将来の蒸し返し・スコープ膨張を防ぐ。

| 不採用機能 | 理由 |
|---|---|
| リアルタイム通知 / Socket.io | リアルタイムは対象外（要件定義書 §5）。Socket.io は Node 製で Spring スタックに乗らない。**通知は F-NOTIF-01 のポーリング**で実現 |
| GitHub ログイン（OAuth） | **招待制・管理者発行**（F-AUTH-02）の閉域モデルと矛盾。GitHub *連携*（F-GH-01）は別物で Phase 3 |
| 公開ポートフォリオ / OGP / PDF出力 / URL共有 / 多言語 / PWA / オフライン | 外部公開・SEO・採用向けは対象外（要件定義書 §5、クローズド前提） |
| 通報 / スパム検知 / 多重アカウント検知 / 荒らし検知 / ブロック / NGワード | 5〜30 人の招待制・実名クラスメイトの閉域では**閉じていること自体が抑止**。公開SNS向けの道具で、S軸（認可）から労力が分散する |
| 学習日記 / 振り返り / ToDo / カンバン / 進捗率 / 開発ログ | **task-board（タスク管理）の領分**。二重実装を避け、必要なら Phase 3 でリンク連携 |
| 他者比較ランキング / トレンド / 貢献度ランキング | 「成長記録が主役・非競争・初心者が傷つかない（R-02）」と緊張。**自分の積み上げ可視化（F-STREAK-01）は採用**するが、他者比較は不採用 |
| 匿名レビュー | 実名クラスメイトの閉域では責任の所在が曖昧になる。心理的安全は F-SAFE-01（辛口OK/優しめ希望）で担保 |
| AI レビュー補助（観点提案/要約/README改善等） | 学習価値はあるがスコープ大・API コスト（月 $0.5 制約）・Phase 3 以降向き。本書では不採用 |

## 共通仕様

### 認可ルール（★S軸・全エンドポイント共通）

すべての API は以下の順で必ず検証する（要件定義書 §3-2、母 SEC-2/3/4）：

1. **ログイン必須**（未ログインは 401）
2. **RBAC**：ロール（受講生/講師）で操作可否を一元判定。最終評価・承認（F-EVAL-01）は講師のみ
3. **所有者 / cohort 一致**：「自分のものか」「同 cohort か」をバックエンドで検証。**不一致は 404**（存在を漏らさず IDOR を遮断）
4. クライアントから渡る `userId` / `cohortId` を信用せず、認証済みコンテキストから導出する

> `F-AUTH` `F-POST` `F-REV` `F-EVAL` `F-PROF` の全エンドポイントに、正常系＋他人/他 cohort アクセスの**拒否系**認可テストを書く（要件定義書 §4-1）。

### エラーレスポンス共通フォーマット

```json
{ "error": { "code": "FORBIDDEN", "message": "この操作を行う権限がありません" } }
```

- 401 未認証 / 403 認可不可（ロール不足）/ 404 リソース無し or 他 cohort（IDOR 遮断）/ 400 バリデーション / 429 レート超過

### レート制限・ログ

- レート制限：ログイン・投稿・レビュー作成に IP+ユーザー単位の制限（母 SEC）
- ログ：主要操作に `duration_ms`（P95 監視・要件定義書 §4-4）、認可境界の操作は監査ログ（誰が・いつ・誰の資源に・何を）

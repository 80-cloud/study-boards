# 面接対策ノート — 用語と設計判断

> 目的：転職面接で「①AI生成の疑念」「②深掘り耐性」を払拭する。
> 暗記でなく理解。覚えるのは**各行の「一言で言うと」だけ**。本番は一言を言ってから、聞かれたら足す。
> 例え話は使わない（本番で使わないため）。難易度は junior〜未経験レベル。

---

## 使い方
- 用語は **3列テーブル（用語 / 一言で言うと / 役割）** で覚える。覚えるのは「一言で言うと」だけ。
- 設計判断は **1行アンカー** で覚える。詰まったら理屈から再構築する。
- 「もっと詳しく」が必要なときだけ、各項の下の補足を読む。

## 1. 認証・セキュリティ用語（面接頻出）

| 用語 | 一言で言うと | 役割（面接での使いどころ） |
|---|---|---|
| トークン | ログイン済みの証明書（文字列） | 毎回パスワードを送らず本人確認する |
| Cookie | ブラウザが自動で送る保存データ | ログイン情報の保存によく使う |
| HttpOnly | JSから読めないCookieの設定 | トークンを盗まれにくくする |
| localStorage | JSから読める保存場所（だから危険） | トークン保存には不向き |
| JWT | 署名付きで偽造できないトークン | 中身を書き換えるとバレる＝詐称できない |
| XSS | 悪意あるJSを撃ち込む攻撃 | 入力をそのまま画面に出すと起きる。対策→無害化して表示 |
| SQLインジェクション | 不正なSQLを注入してDBを操作する攻撃 | 入力をSQLに直に埋めると起きる。対策→値はバインドで渡す |
| CSRF | 利用者に意図しないリクエストを送らせる攻撃 | 対策→トークン確認・SameSite Cookie |
| CORS | 別サイトからのAPI通信を制御する仕組み | これだけ攻撃でなく**防御の仕組み** |
| IDOR（アイドア） | URLのID書き換えで他人の資源に到達 | 認可チェック漏れで起きる。Insecure Direct Object Reference |
| 認証 / 認可 | 認証=誰か / 認可=何をしてよいか | 「ログインできる」と「操作できる」は別 |

### 混同しやすい所（面接の差がつく）
- XSS と SQLi … XSS=ブラウザを攻撃 / SQLi=DBを攻撃（**撃つ場所が違う**）
- XSS と CSRF … XSS=スクリプトを撃ち込む / CSRF=本人になりすまして勝手にリクエスト
- CORS だけは攻撃ではない … 他は攻撃名、CORSは防御の仕組み

## 2. 設計判断の1行アンカー（①cohort境界 IDOR防御）

| 核 | 暗記する1行 |
|---|---|
| 核1 トークンの出所 | 自己申告は信じない、改ざんできない身分証(JWT)だけ見る |
| 核2 認可の一元化 | チェックは30箇所に散らさず1箇所に。散らすと1個書き忘れて穴になる |
| 核3 403 vs 404 | 見せちゃダメな物は「無い」と答える(404)。403は「ここに何かある」とバレる |
| 核4 レビューの境界 | レビューは期(cohort)を持たない。親の投稿をたどって(orJOINして)期を確認 |

### 模範解答セット：IDOR / cohort境界の質問
**質問**：URLのIDを書き換えて他人のデータにアクセスしようとしたらどうなる？対策は？

**この回答に出てくる用語**

| 用語 | 一言で言うと | 役割（この回答での使いどころ） |
|---|---|---|
| IDOR（アイドア） | URLのID書き換えで他人の資源に到達する攻撃 | この質問で問われている攻撃そのもの |
| cohort（読み：コホート） | 利用者が所属する「期・クラス」の単位 | 「同じcohortの中だけ見られる」と境界を作る。面接でもcohortのまま言ってOK |
| 認可チェック | この人がこの操作をしてよいか確認すること | サーバー側で「自分のcohortのデータか」を確認 |
| 404 | 「そんなデータは無い」という返事 | 見せちゃダメな物に返す（存在を隠す） |
| JWT | 署名付きで偽造できないトークン | cohortをここから取る→利用者が偽れない |
| 親の投稿（post） | レビューがぶら下がっている元の投稿 | レビューは期を持たない→親の投稿をたどって期を判定 |
| 外部キー（foreign key） | 「どの親にぶら下がるか」を指す列 | レビューの postId が投稿を参照。親子をつなぐ |
| 親レコード / 親子関係(1対多) | 参照される元のデータ／1投稿に複数レビュー | 「親の投稿」のIT用語。JOINでたどる |
| JOIN（ジョイン） | 親子のテーブルをつなげて一緒に取る操作 | 親投稿のcohortを見るときに使う |

**2つの「期(cohort)の出どころ」を混同しない（重要）**
- JWT → **自分（ログイン中の人）がどの期か**を教える
- 親の投稿 → **そのレビューがどの期のものか**を教える

**模範解答（口頭イメージ）**：
「これはIDOR（アイドア）という攻撃ですね。URLのIDを書き換えて他人の資源にアクセスしようとするものです。でも私のアプリでは、サーバー側で『そのデータがログイン中の人の所属する期(cohort)のものか』を必ずチェックしています。なので他人の（他の期の）IDを指定しても『そんなデータは無い』として404を返します。しかも、その人がどの期に属するかはログイン時に発行した署名付きトークン（JWT）から取っているので、利用者が勝手に偽ることもできません。」

**構造（これだけ覚える）**：①IDORという攻撃 → ②サーバーでcohortチェック → ③他人のは404 →（+α）cohortはJWTから取るので偽れない

### Q1の答え（トークン保存）
- 結論：localStorage でなく **HttpOnly Cookie** に保存。
- 理由：localStorage は JS から読めるので、XSS が起きるとトークンを盗まれる。HttpOnly Cookie は JS から読めないので盗まれない。
- 1行：**「localStorageはJSから盗める。HttpOnly Cookieは盗めない」**

## 4. DB・アーキ・インフラ用語（面接頻出・junior）

| 用語 | 一言で言うと | 役割（面接での使いどころ） |
|---|---|---|
| 3層アーキテクチャ | Controller / Service / Repository に分ける構成 | 役割を分け、修正・テストをしやすくする（責任分離） |
| DTO | 外部に返す用の入れ物 | Entity（DB直結）をそのまま返さず、内部情報を隠す |
| Entity | DBのテーブルと対応するオブジェクト | DBの1行を表す。外には直接出さない |
| N+1問題 | 最初の1回＋件数分の追加クエリが出る問題 | 一覧取得で多発。対策→JOINでまとめて取る |
| トランザクション | 複数の操作を全部成功か全部失敗にする仕組み | 途中で中途半端な状態を残さない |
| インデックス | 検索を速くする仕組み | 読みが速くなる代わり、書き込みは少し遅い。必要な所だけ |
| 主キー | データ1件を一意に識別する列 | id など。1件を確実に指定できる |
| Docker | アプリを環境ごとパッケージ化する技術 | 「自分のPCでは動く」をなくす（環境差をなくす） |
| CI | 変更を自動で検証する仕組み | 品質保証。マージ前後に走る |
| CD | 検証済みコードを環境へ届ける仕組み | 配送保証。デプロイ |

### HTTPまわり（超頻出）
| 用語 | 一言で言うと | 役割 |
|---|---|---|
| HTTP / HTTPS | HTTPSは通信を暗号化したHTTP | 盗み見を防ぐ。今はほぼHTTPS |
| 200 / 400 / 404 / 500 | 成功 / リクエスト不正 / 無い / サーバー側エラー | サーバーの返事の種類 |
| 401 / 403 | 401=未認証（誰か不明） / 403=認証済みだが権限なし | 「ログインしてない」と「権限がない」は別 |

### Git・開発フロー（超頻出）
| 用語 | 一言で言うと | 役割 |
|---|---|---|
| push（プッシュ） | コードをGitHub（みんなの保管場所）に送る | 自分のPCの中→みんなが見える状態に |
| ブランチ | 作業用に枝分かれした作業場所 | 本番(main)を壊さず作業する |
| main | みんなが使う本番の土台ブランチ | ここが壊れると全員困る |
| 直接push（直push） | 確認を飛ばしていきなりmainに入れること | レビューなし＝壊れたコードが混ざる危険 |
| PR（プルリクエスト） | 「mainに入れていい?」と確認を頼むこと | マージ前にレビューできる |
| マージ | 確認OKのコードをmainに取り込むこと | PRが承認されたら実行 |
| コミット | 変更を1区切りとして記録すること | メッセージで「何を変えたか」を残す |

## 補足A. 必須の基礎用語（土台。これが曖昧だと上が崩れる）

| 用語 | 一言で言うと | 役割 |
|---|---|---|
| HTML | ページの骨組み・中身 | 見出し・ボタン・文章を置く |
| CSS | ページの見た目・装飾 | 色・大きさ・配置を整える |
| JavaScript (JS) | ブラウザの中で動くプログラミング言語 | 画面を動かす・データを処理する |
| React | JSを便利に書く道具 | JSの一種。review-boardのフロント |
| SQL | DBに命令を出す言語 | データの追加・取得・更新・削除 |
| API | アプリ同士をつなぐ窓口 | フロントがバックにデータを頼む入口 |
| JSON | データのやり取り形式 | フロント⇔バックでデータを渡す書き方 |

### 一文まとめ
- **HTMLで作って、CSSで飾って、JavaScriptで動かす。**
- 「JSから読める/読めない」= JavaScriptのプログラムから中身が見えるかどうか（セキュリティの分かれ目）。

## 3. 復習用 問題集（これまで出した問題）

> 使い方：問題だけ見て口頭で答える → 下の「答え」で照合。答えは一言だけ覚える。

### 用語クイズ（基礎の確認）
- Q. IDOR とは？ → A. URLのID書き換えで他人の資源に到達する脆弱性
- Q. RBAC とは？ → A. ロール（役割）ごとに権限を定める方式
- Q. 権限のない資源に 404 を返す狙いは？ → A. 資源の「存在」を漏らさないため（403だと存在がバレる）
- Q. このアプリで cohortId はどこから取る？ → A. 検証済みのJWT（AuthPrincipal）から。クライアントは詐称できない
- Q. 最小権限の原則とは？ → A. 各主体に必要最小限の権限だけ与える
- Q. 権限昇格とは？ → A. 本来持たない上位の権限を不正に取得すること
- Q. 多層防御とは？ → A. 独立した防御層を複数重ね、一つ破られても全体を守る
- Q. reviewsはcohortIdを持たないが集計で境界を守る手段は？ → A. review.postId→post.cohortId を JOIN で絞る

### 設計判断（分かれ道）
- Q. 権限のない人に 403 と 404 どちらを返す？なぜ？ → A. 404。403は「ここに何かある」と存在がバレ、列挙攻撃の手がかりになる
- Q. 認可チェックを各エンドポイントに散らす vs 1箇所に集約、どっち？ → A. 1箇所に集約（認可の一元化）。散らすと1個書き忘れてIDORの穴になる

### 面接頻出
- Q. トークンをブラウザのどこに保存？なぜlocalStorageでない？ → A. HttpOnly Cookie。localStorageはJSから読めXSSで盗まれる。HttpOnly Cookieは読めない
- Q. XSS とはどういう攻撃か？ → A. 悪意あるJSを撃ち込み、他の利用者のブラウザで実行させる攻撃。結果→Cookie/トークンを盗まれる
- Q. XSS対策は？自分のアプリでは？ → A. 入力をそのまま出さず無害化（エスケープ）して表示。スクリプトもただの文字として見えるだけで実行されない。Reactは自動でエスケープするのでデフォルトで強い（dangerouslySetInnerHTMLだけ注意）
- Q. プライベートな資源の権限チェックはフロント/バックどちら？漏れると何が起きる？ → A. バックエンド（フロントは書き換えられるのでUX補助のみ）。漏れるとIDOR（URL書き換えで他人の資源が見える）が成立

### 新規追加問題（DB・アーキ・インフラ・HTTP）
- Q. 3層アーキテクチャの3つの役割は？ → A. Controller=受付 / Service=処理・ルール / Repository=DBアクセス。役割を分けて修正・テストしやすくする
- Q. なぜEntityでなくDTOを返す？ → A. DB直結のEntityをそのまま返すと内部情報が漏れる。外部用に整えた入れ物（DTO）で返す
- Q. N+1問題とは？ → A. 最初の1回＋件数分の追加クエリが出て遅くなる問題。対策→JOINでまとめて取る
- Q. トランザクションとは？なぜ必要？ → A. 複数操作を全部成功か全部失敗にする。途中の中途半端な状態を残さないため
- Q. インデックスとは？デメリットは？ → A. 検索を速くする仕組み。書き込みが少し遅くなるので必要な所だけ付ける
- Q. なぜファイルをDBでなくS3に置く？ → A. DBが肥大化して遅くなるのを防ぐ。S3は大容量に強く安い
- Q. Dockerのメリットは？ → A. 環境ごとパッケージ化して「自分のPCでは動く」をなくす（環境差をなくす）
- Q. CIとCDの違いは？ → A. CI=自動で検証（品質保証）/ CD=環境へ届ける（配送・デプロイ）
- Q. なぜmainブランチに直接pushしない？ → A. mainはみんなが使う土台。直pushは確認なしで壊れた/いらないコードが混ざる。PRで確認してからmainに入れる（自分のアプリでも実践）
- Q. なぜコミットメッセージを丁寧に書く？ → A. 後で読む人（未来の自分・仲間・不具合調査時）が「何を変えたか」すぐ分かるように
- Q. Git（バージョン管理）の何が嬉しい？無いと困ることは？ → A. 変更履歴を記録する。無いと「いつ・何が・どう変わったか」分からず不具合の解明・復旧に時間がかかる。失敗しても前の状態に戻せるのも大きい
- Q. なぜExcel/CSVでなくデータベース？ → A. 大量データに強い・検索が速い・複数人が同時に使っても壊れない・正確さを保つルールを決められる
- Q. 2人が同時に保存してもDBが大丈夫な理由は？ → A. 同時に来た処理を順番にきちんとさばき、データが矛盾しないように守る（トランザクション）。Excelは後の人が上書きして片方が消える
- Q. HTTPとHTTPSの違いは？ → A. HTTPSは通信を暗号化したHTTP。盗み見・改ざんを防ぐ
- Q. 401と403の違いは？ → A. 401=未認証（誰か不明・ログインが必要）/ 403=認証済みだが権限がない

## 学習方針（メタ・忘れないため）
- 暗記する量は最小（一言 or 1行アンカー）。本番の緊張でど忘れしても再構築できる形にする。
- 結論ファーストで言う → 「具体的には?」と聞かれたら足す（対話のキャッチボール）。
- 完璧な暗唱より、詰まりながら自分の言葉で言う方が「人間が作った」証拠になり、①の疑念が晴れる。
- **「間の説明文」は暗記しない・捨てる**（最大の発見）。答えは3層に分ける：
  - 核（単語）＝覚える / 結論文（短い）＝覚える / 間の説明文＝**覚えない**
  - 例：「スクリプトもただの文字として見えるだけで実行されない」は暗記対象外。
  - 間が必要なのは「具体的には?」と聞かれた時だけ。その時は**仕組みの理解から その場で作る**（文を暗記しない）。
  - 例：XSS対策の答えは「そのまま出さず、Reactで自動でエスケープします」だけで満点。長く言おうとしない。

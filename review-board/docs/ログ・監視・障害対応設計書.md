## 1. 監視とオブザーバビリティの区別（§3-1）

- **監視（Monitoring）**：既知の問題を見張る（例：ヘルスチェック、エラー率の閾値アラート）。
- **オブザーバビリティ（Observability）**：未知の事象も後から調査できる（構造化ログ・トレース・メトリクスで「なぜ」を追える）。
- review-board は 重点軸（認可）が突出点のため、**「誰が・何に・何をしたか」の追跡（audit_logs）を監査の中核**に置き、運用診断ログと役割を分ける（§3）。

## 2. 4 ゴールデンシグナル（§3-1）

| シグナル | review-board での観点 | 現状（#121 実装後） | 残り（Phase3） |
|---|---|---|---|
| Latency（遅延） | 投稿一覧・成長記録の API 応答（P-1 目標と対） | ✅ `http.server.requests` をヒストグラムで収集（P95/P99 算出可） | P-1 目標値との突合・自動アラート |
| Traffic（流量） | ログイン・投稿・レビュー・評価のリクエスト数 | ✅ `http.server.requests` の count | — |
| Errors（エラー） | 5xx・認可失敗（401/403/404）の発生率 | ✅ アプリログ＋`http.server.requests` の status タグで率を算出可 | エラー率アラート（閾値超で通知） |
| Saturation（飽和） | DB コネクションプール（Hikari）・JVM ヒープ | ✅ `hikaricp_connections`・`jvm_memory_used_bytes` を公開 | 飽和アラート |

> リアルタイム機能（WebSocket 等）は要件で対象外のため、接続数・配信遅延の監視は不要（§3-1 の該当項は N/A）。

## 3. ログ設計

### 3-1. ログの種類と役割分担（重要）

review-board は2系統のログを**役割で分離**する。混同しないこと。

| 種類 | 目的 | 保存先 | 内容 | 現状 |
|---|---|---|---|---|
| **アプリログ** | 運用診断（なぜ失敗したか） | 標準出力（SLF4J/Logback） | 例外スタック・処理の節目・起動/シード | ✅ あり（Spring Boot 既定 + `DevDataSeeder` 等） |
| **監査ログ** | ★重点軸の証跡（誰が・誰の資源に・何を） | `audit_logs` テーブル | actor/action/target/cohort/時刻 | ✅ あり（`AuditService`・操作と同一 TX で記録） |

> **使い分けの原則**：セキュリティ上「誰が何をしたか」を追うのは **audit_logs**（改ざん耐性・クエリ可能・cohort 境界つき）。
> 「処理がなぜ落ちたか」を追うのは **アプリログ**。前者は §脅威モデリング T-6 の否認対策、後者は障害診断のため。

### 3-2. 構造化ログと追跡性（§3-1）

- **実装済（#121）**：
  - **MDC に requestId（リクエスト相関 ID）と userId を自動付与**する `MdcLoggingFilter` を追加（`JwtAuthenticationFilter` の後段。SecurityContext 確立後に userId を載せる）。
  - requestId は受信した `X-Request-Id` を尊重し、無ければ UUID を採番。レスポンスにも同名ヘッダで返す（LB/フロント由来の ID を引き継いで横断追跡）。
  - userId は検証済み `AuthPrincipal` から導出（クライアント入力ではない）。未認証なら付与しない。
  - dev はプレーンログに `[requestId,userId]` を表示（`logging.pattern.correlation`）。**prod プロファイルは JSON 構造化ログ（ECS 形式）**で機械解析可能（M-5 の dev/prod 分離）。
  - 機密（パスワード・トークン・JWT secret）は MDC・ログに出さない（SEC-9 の延長）。

### 3-3. ログレベル方針

| レベル | 用途 |
|---|---|
| ERROR | 想定外の例外・5xx・refresh トークン reuse 検知（セキュリティ事象） |
| WARN | 想定内だが注意すべき事象（SEED_PASSWORD 未設定でシードスキップ等） |
| INFO | 起動・シード・主要なライフサイクル |
| DEBUG | 開発時のみ（本番では出さない。dev/prod をプロファイルで分離＝M-5） |

## 4. 監視エンドポイント（Actuator）

- **実装済（#121）**：`health` / `info` に加え `metrics` / `prometheus`（Micrometer）を公開し、4ゴールデンシグナルを収集。
- **公開範囲を絞る（SEC-2/SEC-11）**：`health` は監視プローブ用に未認証開放、`metrics` / `prometheus` は **`ROLE_TEACHER`（運用ロール）限定**（`SecurityConfig` の `/actuator/**`）。受講生・未認証に JVM ヒープ・Hikari プール・流量を見せない。
  - 統合テスト `ObservabilityIntegrationTest` で 401（未認証）/403（受講生）/200（講師）を回帰検証。

## 5. アラート → Runbook → 復旧（§3-1）

「鳴らして終わり」にせず、重大度判定 → Runbook（対処手順）→ 復旧まで定義する。以下は review-board で起こりうる代表シナリオの Runbook。

| シナリオ | 兆候 | 重大度 | Runbook（対処） |
|---|---|---|---|
| DB 接続不可 | 起動時 Flyway/Hikari が接続失敗・`/actuator/health` が DOWN | 高 | ① DB コンテナ稼働確認（`docker ps`）② パスワード/接続情報（env）確認 ③ 復旧後アプリ再起動。詳細は §6 の障害報告書へ |
| JWT secret 未設定/短すぎ | 起動時 `IllegalStateException`（fail-fast） | 高 | env `JWT_SECRET`（32文字以上）を設定して再起動。**fail-fast は仕様**（弱い鍵で起動させない） |
| ポート競合（8082/5175/5434） | bootRun/vite が `Address already in use` | 中 | CLAUDE.md §10 に従い該当 PID を停止して**正規ポートで再起動**（別ポート起動は禁止＝CORS/プロキシ崩壊） |
| refresh トークン reuse 検知 | `RefreshTokenService` が当該ユーザー全失効・ERROR ログ | 中（セキュリティ） | 当該ユーザーに再ログインを促す。盗用の疑いとして audit_logs と併せて調査 |
| 認可エラー急増（403/404） | エラー率上昇 | 中 | IDOR 攻撃の試行か正当な誤操作かを audit_logs で切り分け |
| 依存脆弱性 High/Critical 検出 | 依存スキャン CI が fail | 中 | 修正版へ更新（PR #102 と同手順）。CI を 0 件 green に戻す |
| 非正規化カウンタの drift | 定期再計算バッチ（#129）が `counter drift 検出` を WARN ログ出力 | 低（気づき） | 単発なら競合・部分失敗の補正で問題なし。**継続的に同じ counter が出るなら同一 TX 更新のバグを疑う**（例：レビュー削除時に thanks_received_count を減算していない既知ギャップ＝バッチが補正中。本実装で in-TX 側も修正検討） |

## 6. 障害対応プロセス（family / 共通方針の継承）

### 6-1. インシデント・ライブラリ（症状 → 兆候 → 真因）

task-board `docs/incidents/` の運用を継承する。**新しい異常に直面したら、まず過去ケースを「症状 → 兆候 → 真因」の3段階で照合**する（単純な1対1比較は誤診の元）。review-board 固有のケースが出たら `review-board/docs/incidents/` を新設して記録する（解決後に追加）。

### 6-2. 障害対応報告書

重大インシデントは共通方針の障害対応報告書テンプレート（16章構造：概要・時系列・原因・改善サイクル 本質的振り返り・やらなかったことの振り返り・成功要因・運用フェーズ継続観察 等）に従って記録する。

### 6-3. 本セッションで実地に遭遇した事象（参考ケース）

実装中に観測した事象を、上記プロセスの実例として残す：

| 症状 | 真因 | 是正処置 |
|---|---|---|
| `Could not find a valid Docker environment`（テスト全滅） | Docker Desktop の API 上限超を docker-java が要求（400） | `api.version` を保守的に固定（build.gradle） |
| 既存テストが FK 違反で落ちる | テスト間クリーンアップの順序ミス（子→親） | `AbstractIntegrationTest` で FK 依存順クリーンアップを集約 |
| `Could not open JPA EntityManager`（クラス間） | 共有 `@Container` がクラス毎に停止 | singleton container パターン |
| ビルド破壊（`* 2.java`） | iCloud 同期由来の重複ファイル | 重複を Trash 退避（`brctl`/Finder） |

## 7-1. 実装対応表（CloudWatch アラーム × 設計上のシグナル）

Issue #480 / PR で `infra/cloudwatch.tf` と `infra/sns.tf` を整備し、設計と実装の対応を 1 対 1 で明示する。通知先は既存 `var.budget_notify_email`（Budgets と同じ宛先＝運用宛先の単一化）。

| # | 設計シグナル（§5 アラート） | 実装した CloudWatch alarm | メトリクス | 閾値 | 評価期間 |
|---|---|---|---|---|---|
| 1 | サービス断（インスタンス障害） | `${name_prefix}-ec2-status-check-failed` | `AWS/EC2 StatusCheckFailed` | > 0 | 1 期間 / 300s |
| 2 | アプリ過負荷（CPU 飽和） | `${name_prefix}-ec2-cpu-high` | `AWS/EC2 CPUUtilization` | ≥ 80% | 3 期間 / 300s |
| 3 | DB 過負荷 | `${name_prefix}-rds-cpu-high` | `AWS/RDS CPUUtilization` | ≥ 80% | 3 期間 / 300s |
| 4 | DB 容量枯渇 | `${name_prefix}-rds-free-storage-low` | `AWS/RDS FreeStorageSpace` | < 1 GB | 1 期間 / 300s |
| 5 | DB コネクション枯渇予兆 | `${name_prefix}-rds-connections-high` | `AWS/RDS DatabaseConnections` | ≥ 64（t3.micro max ≈ 80 の 80%） | 3 期間 / 300s |

通知先は SNS トピック `${name_prefix}-alerts`（[infra/sns.tf](../infra/sns.tf)）。将来 Slack / PagerDuty を追加する場合は subscription を増やすだけで、各 alarm の `alarm_actions` は不変（`output "alerts_topic_arn"` で公開済み）。

> 引き継ぎ書 #6 の「ALB 5xx」「ECS 健全性」は本構成（EC2 単体・ALB/ECS 無し）にそぐわないため、EC2/RDS 寄りに置換した。冗長化フェーズで ALB / ECS / Auto Scaling を導入する際に「ALB 5xx 率」「ターゲット健全数」「タスク running < desired」を追加する。

## 1. 監視とオブザーバビリティの区別（母 §3-1）

- **監視（Monitoring）**：既知の問題を見張る（例：ヘルスチェック、エラー率の閾値アラート）。
- **オブザーバビリティ（Observability）**：未知の事象も後から調査できる（構造化ログ・トレース・メトリクスで「なぜ」を追える）。
- review-board は S軸（認可）が突出点のため、**「誰が・何に・何をしたか」の追跡（audit_logs）を監査の中核**に置き、運用診断ログと役割を分ける（§3）。

---

## 2. 4 ゴールデンシグナル（母 §3-1）

| シグナル | review-board での観点 | 現状 | 本実装で追加 |
|---|---|---|---|
| Latency（遅延） | 投稿一覧・成長記録の API 応答（P-1 目標と対） | 未計測 | Actuator `metrics`/Micrometer + P95 監視 |
| Traffic（流量） | ログイン・投稿・レビュー・評価のリクエスト数 | 未計測 | Micrometer counter |
| Errors（エラー） | 5xx・認可失敗（401/403/404）の発生率 | アプリログに出力 | エラー率アラート（閾値超で通知） |
| Saturation（飽和） | DB コネクションプール（Hikari）・JVM ヒープ | 未計測 | Actuator `metrics` で pool/heap 監視 |

> リアルタイム機能（WebSocket 等）は要件で対象外のため、接続数・配信遅延の監視は不要（母 §3-1 の該当項は N/A）。

## 3. ログ設計

### 3-1. ログの種類と役割分担（重要）

review-board は2系統のログを**役割で分離**する。混同しないこと。

| 種類 | 目的 | 保存先 | 内容 | 現状 |
|---|---|---|---|---|
| **アプリログ** | 運用診断（なぜ失敗したか） | 標準出力（SLF4J/Logback） | 例外スタック・処理の節目・起動/シード | ✅ あり（Spring Boot 既定 + `DevDataSeeder` 等） |
| **監査ログ** | ★S軸の証跡（誰が・誰の資源に・何を） | `audit_logs` テーブル | actor/action/target/cohort/時刻 | ✅ あり（`AuditService`・操作と同一 TX で記録） |

> **使い分けの原則**：セキュリティ上「誰が何をしたか」を追うのは **audit_logs**（改ざん耐性・クエリ可能・cohort 境界つき）。
> 「処理がなぜ落ちたか」を追うのは **アプリログ**。前者は §脅威モデリング T-6 の否認対策、後者は障害診断のため。

### 3-2. 構造化ログと追跡性（母 §3-1・B-Q26）

- **現状**：プレーンテキストログ（Logback 既定）。requestId/userId の自動付与は未実装。
- **本実装で追加**：
  - JSON 構造化ログ（機械解析可能）。
  - **MDC に requestId（リクエスト単位の相関 ID）と userId を自動付与**するフィルタを追加し、1リクエストのログを横断追跡できるようにする。userId は検証済み `AuthPrincipal` から。
  - 機密（パスワード・トークン・JWT secret）はログに出さない（SEC-9 の延長）。

### 3-3. ログレベル方針

| レベル | 用途 |
|---|---|
| ERROR | 想定外の例外・5xx・refresh トークン reuse 検知（セキュリティ事象） |
| WARN | 想定内だが注意すべき事象（SEED_PASSWORD 未設定でシードスキップ等） |
| INFO | 起動・シード・主要なライフサイクル |
| DEBUG | 開発時のみ（本番では出さない。dev/prod をプロファイルで分離＝M-5） |

## 4. 監視エンドポイント（Actuator）

- **現状**：`application.yml` で `health` / `info` のみ公開。
- **本実装で追加**：`metrics` / `prometheus`（Micrometer）を**認証済み・運用ネットワーク限定**で公開し、4ゴールデンシグナルを収集。公開範囲は SEC-2/SEC-11 の精神で絞る（誰でも metrics を見られる状態にしない）。

## 5. アラート → Runbook → 復旧（母 §3-1）

「鳴らして終わり」にせず、重大度判定 → Runbook（対処手順）→ 復旧まで定義する。以下は review-board で起こりうる代表シナリオの Runbook。

| シナリオ | 兆候 | 重大度 | Runbook（対処） |
|---|---|---|---|
| DB 接続不可 | 起動時 Flyway/Hikari が接続失敗・`/actuator/health` が DOWN | 高 | ① DB コンテナ稼働確認（`docker ps`）② パスワード/接続情報（env）確認 ③ 復旧後アプリ再起動。詳細は §6 の障害報告書へ |
| JWT secret 未設定/短すぎ | 起動時 `IllegalStateException`（fail-fast） | 高 | env `JWT_SECRET`（32文字以上）を設定して再起動。**fail-fast は仕様**（弱い鍵で起動させない） |
| ポート競合（8082/5175/5434） | bootRun/vite が `Address already in use` | 中 | CLAUDE.md §10 に従い該当 PID を停止して**正規ポートで再起動**（別ポート起動は禁止＝CORS/プロキシ崩壊） |
| refresh トークン reuse 検知 | `RefreshTokenService` が当該ユーザー全失効・ERROR ログ | 中（セキュリティ） | 当該ユーザーに再ログインを促す。盗用の疑いとして audit_logs と併せて調査 |
| 認可エラー急増（403/404） | エラー率上昇 | 中 | IDOR 攻撃の試行か正当な誤操作かを audit_logs で切り分け |
| 依存脆弱性 High/Critical 検出 | 依存スキャン CI が fail | 中 | 修正版へ更新（PR #102 と同手順）。CI を 0 件 green に戻す |

## 6. 障害対応プロセス（family / 修練城の継承）

### 6-1. インシデント・ライブラリ（症状 → 兆候 → 真因）

task-board `docs/incidents/` の運用を継承する。**新しい異常に直面したら、まず過去ケースを「症状 → 兆候 → 真因」の3段階で照合**する（単純な1対1比較は誤診の元）。review-board 固有のケースが出たら `review-board/docs/incidents/` を新設して記録する（解決後に追加）。

### 6-2. 障害対応報告書

重大インシデントは修練城の障害対応報告書テンプレート（16章構造：概要・時系列・原因・PDCAS 本質的振り返り・やらなかったことの振り返り・成功要因・運用フェーズ継続観察 等）に従って記録する。

### 6-3. 本セッションで実地に遭遇した事象（参考ケース）

実装中に観測した事象を、上記プロセスの実例として残す：

| 症状 | 真因 | 是正処置 |
|---|---|---|
| `Could not find a valid Docker environment`（テスト全滅） | Docker Desktop の API 上限超を docker-java が要求（400） | `api.version` を保守的に固定（build.gradle） |
| 既存テストが FK 違反で落ちる | テスト間クリーンアップの順序ミス（子→親） | `AbstractIntegrationTest` で FK 依存順クリーンアップを集約 |
| `Could not open JPA EntityManager`（クラス間） | 共有 `@Container` がクラス毎に停止 | singleton container パターン |
| ビルド破壊（`* 2.java`） | iCloud 同期由来の重複ファイル | 重複を Trash 退避（`brctl`/Finder） |

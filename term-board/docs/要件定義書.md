## 第0項：オールA宣言 ＋ S軸宣言

> 母要件定義書 §0-3・§4-1 第0項に従い、本子が継承する品質の床と、突出させる軸を明記する。

### 継承宣言（オールA＝床）

本アプリは母要件定義書 v0.1 を継承し、品質4軸すべてを **A 以上（弱点ゼロの床）** に保つことを目標とする。
ただし本MVPは **バックエンド・DB・認証を持たない静的SPA** であるため、母の MUST のうち
サーバー・DB・認証を前提とする要件は現時点で適用対象がない。これらは「未達（床割れ）」ではなく
**「適用対象なし（N/A）＋将来の多人数化フェーズで有効化」** として §逸脱記録 に明示し、
`api/` 層の隔離設計（§8）によって**作り直しゼロで再有効化できる**状態を維持する。
適用対象がある軸（保守性・性能・UX・フロントのセキュリティ＝XSS/依存脆弱性）は母の MUST を満たす。

### S軸宣言：性能・UX を S へ

本アプリの目玉（差別化）は「**用語を「見た瞬間に分かり、面接で言える」まで運ぶ、軽快で続けたくなる学習体験**」である。
学習アプリの価値は機能の華やかさではなく「ストレスなく何度も回せること」にある（過去問道場が支持される理由）。
よって品質4軸のうち **性能・UX を S** とする。

**S基準（測定可能な形・付録A S判定表に転記）：**
- Lighthouse（モバイル）で **Performance ≥ 90 / Best Practices ≥ 90 / Accessibility = 100** を達成する（母 P-9・P-1）
- アクセシビリティは **WCAG 2.1 Level AA 相当**（label・alt・キーボードのみで全操作可能・色のみに依存しない正誤表示・コントラスト比 AA）
- 採点フィードバックは**即時**（ローカル判定のため知覚遅延ゼロ＝操作応答 < 100ms）／初回表示 < 1.5s（標準回線）
- 「分野別正答率」「苦手用語の自動抽出」を表示し、学習者が次に何をやればいいか**1画面で分かる**

### 床を割らない約束（Sの代償に A 未満へ落とさない軸）

性能・UX を S へ引き上げる代償として、以下を A 未満に落とさないことを約束する：
- **保守性**：データ取得を `api/` 層へ隔離し（母 M-11）、画面・ロジック・データを責任分離する（母 M-3）。
  「速さ・手軽さ」のために層を溶かさない。TypeScript で型安全を保つ（母 M-12）
- **セキュリティ**：用語・解説はプレーンテキストとしてフレームワークの自動エスケープに委ね、
  `dangerouslySetInnerHTML` を使わない（母 SEC-5）。依存脆弱性スキャン（`npm audit`）を CI に常設し High/Critical 0 件（母 SEC-2系の精神を静的SPAに適用）
- **安定性**：localStorage の破損・容量超過・未対応ブラウザでも**学習機能そのものは停止しない**
  （進捗が壊れても用語の出題は続く＝graceful degradation。母 1-1・1-3）

## 1. プロジェクト概要

### 1-1. 背景・課題

IT業界への就職を目指す学習者にとって、面接では IT用語の理解を**自分の言葉で簡潔に説明できるか**が問われる。
しかし用語集を眺めるだけの暗記は「読めば分かるが、いざ聞かれると言葉が出てこない」状態に陥りやすい。
過去問道場のような4択演習は知識の定着に有効だが、**「選べる」と「面接で言える」の間にはギャップ**がある。

そこで、4択演習で知識を定着させたうえで、**同じ用語を「面接での短い言い方」に変換して練習できる**学習アプリを開発する。

### 1-2. 目的（学習到達点）

> **学習姿勢:** まず Phase 1 で「動いて毎日回せる」ものを作り、Phase 以降で「なぜこの構成か」を
> 自分の言葉で説明できる水準まで深掘る。本アプリ自体が面接で語れる成果物になることも狙う。

#### 学習対象（到達点の具体）

- **React + Vite + Tailwind** によるSPA構築（コンポーネント設計・状態管理・カスタムフック：母 M-3・B-Q16〜18）
- **データ取得の抽象化（`api/` 層の隔離）** を実装し、保存先を localStorage → サーバーへ差し替え可能にする（母 M-11・B-Q15）
- **TypeScript による型安全**（母 M-12）
- **アクセシビリティ（WCAG AA）** とパフォーマンス最適化を実装で達成する（母 P-9・S軸）
- **1つのデータモデルから複数の学習モード**を導出する設計（DRY・関心の分離）
- （将来）認証・DB・サーバーAPI へ拡張する際の移行設計を理解する

### 1-3. 対象ユーザー（v0.3 で明確化）

> **本アプリの対象は「IT業界へ初めて転職する人・実務未経験者」である。** この前提が設計の多くを決める。
> 開発者本人（IT用語の学習者）も一次利用者だが、**作るときは常に「実務経験ゼロの転職者」を想定する**。

- **一次利用者（ペルソナ）**：IT業界へ**初めて**転職しようとする人／実務未経験者。
  - 前提として **自分の実装ポートフォリオ・現場経験を持たない**（例：別業界からの転職、専門学校・独学卒、第二新卒）。
  - 用語を「聞いたことはあるが、面接で説明しろと言われると詰まる」段階にいる。
  - 単一利用者・ログイン不要（MVP）。
- **未経験者を対象にすることで決まる設計前提（重要）**：
  1. **専門用語を専門用語で説明しない**（平易な言葉ファースト）。「TCPは信頼性のあるトランスポート層プロトコル」では未経験者に伝わらない → 「データを"確実に・順番どおり"届ける仕組み」から入る（§4-5・F-TERM-05＝MUST）。
  2. **用語は"自分のコード"ではなく"現場での使われ方シーン"に紐付ける**。未経験者は実装経験がないため、「この用語は現場のどんな場面で出てくるか」のイメージで補う（F-TERM-04）。
  3. **「分かる」より前に「怖くない・続けられる」**。未経験者は専門用語の量に圧倒されやすい → 1問の軽さ・小さな成功体験・進捗の可視化（自信設計）を S軸 UX の一部として扱う。
  4. **面接で問われる"なぜ"に弱い**ため、知識を1段だけでなく深掘り（§13・F-INTV-03）で支える。
- **将来の利用者（MAY）**：同じ目的を持つ他の未経験転職者。多人数化フェーズ（§3 Phase 4）で
  アカウント・サーバー保存を導入した場合に対応する（現時点ではスコープ外だが設計の余地は残す）。

### 1-4. 利用環境

- PC ブラウザ：Chrome / Edge / Safari 最新版
- モバイルブラウザ：iOS Safari / Android Chrome 最新版（**スキマ時間学習を重視しモバイル最適化必須**）
- ネイティブアプリ・オフラインインストール（PWA）は当初対象外（Phase で検討）

### 1-5. 差別化ポイント

母の「不要を切って短所を作らない」思想に従い、本家と意図的に変える点を明記する。

| 項目 | 過去問道場（本家） | term-board（自作） |
|---|---|---|
| 主目的 | 資格試験の合格 | **面接で用語を「言える」ようにする** |
| 出題 | 過去問4択 | 4択（知識定着）＋**暗記カード**＋**面接想定問答** |
| 1データの使い方 | 設問単位 | **1用語 → 3モードで再利用**（§8） |
| 進捗 | 正答率・分野別 | 正答率・分野別＋**苦手用語の自動抽出と再出題** |
| 規模 | 大規模・多人数・サーバー | **単一利用者・静的SPA**（不要な認証/DB/サーバーを意図的に削る）|
| 採点 | サーバー判定 | **ローカル即時判定**（知覚遅延ゼロ＝S軸の根拠） |

> 認証・多人数・サーバー保存を「削る」のは、現時点の目的（自分用の面接対策）に不要で、
> 持つと逆にセキュリティ・運用の攻撃面（床割れリスク）を増やすため。必要になった時点で
> `api/` 層の差し替えで足す（母 §0-3「便利さより安全＝不要を持たない」）。

## 2. 前提条件と制約

- **C-1（保存）**：MVPは永続化を **localStorage** のみで行う。サーバー・DB を持たない。
- **C-2（データ）**：用語データは **静的JSON（またはTS）としてリポジトリに同梱**する。動的更新はしない。
- **C-3（機密情報）**：本MVPは機密情報を扱わない（認証なし・外部APIなし）。将来サーバー化時は母 SEC-9 を厳守。
- **C-4（言語・運用）**：母 M-1/M-2 を継承し、Issueファースト＋PR経由・Conventional Commits（日本語）で開発する。
- **C-5（用語の正確性）**：用語の意味・解説は学習用であり、誤りが面接で不利益になりうる。
  出典・チェック方針を §10 に定め、**内容の正確性レビューを受入条件に含める**。
- **C-6（採用バージョン）**：本プロジェクトは以下の版を採用する。**Java 25 を軸**に Gradle・Spring Boot を整合させ、
  実機ランタイムと build toolchain を一致させる（母 CLAUDE.md §12-4「Toolchainとランタイムの整合」・学習メモ「ランタイム前提を見る」）。

  | 技術 | 採用版 | フェーズ | 整合の根拠 |
  |---|---|---|---|
  | Node.js | **24 LTS**（`.nvmrc` 固定） | MVP | 奇数版（25）＝非LTSを避けビルド再現性を確保 |
  | Vite / React / TypeScript | 各最新安定 | MVP | 新規のため最新でOK |
  | Java | **25（LTS）** | Phase 4 | `languageVersion=25`。**実機にJDK25導入が必要**（現状21のみ） |
  | Gradle | **9.1.0**（wrapper固定） | Phase 4 | JDK25対応。既存（review-board）と同一 |
  | Spring Boot | **3.5系最新パッチ**（現状 3.5.14） | Phase 4 | Java25対応済み・実績あり。4.0系は移行コスト大のため当面見送り |
  | PostgreSQL | **16**（docker `postgres:16`） | Phase 4 | Javaと独立・既存資産と統一・サポート期間内 |

  > **整合の肝:** Java 25 ⇄ Gradle 9.1 ⇄ Spring Boot 3.5.x の3点が噛み合うことを確認済み。
  > Java 25 を正式採用するには実機への JDK 25 導入が前提（現状は `openjdk@21` のみ）。

## 3. 機能要件（Phase別スコープ）

機能IDは母 付録C に従い `F-<ドメイン>-<連番>`。ドメイン：`TERM`（用語データ）／`QUIZ`（4択）／
`CARD`（暗記カード）／`INTV`（面接問答）／`PROG`（進捗＝用語ごとの正誤集計）／`LOG`（学習記録＝時系列の学習の軌跡）／
`BHV`（行動面接＝STAR等の人物面接練習・v0.3追加）／`AUTH`（将来）。

> **v0.3 の追加機能群（§13 で詳述）:** 対象＝未経験者を踏まえ、過去問道場に無い面接対策機能を
> 「コア」「差別化」に分けて追加した。実装時期は下表の Phase に割り振る（MVP＝Phase 1 は据え置き）。

> **PROG と LOG の役割分離:** `F-PROG-*` は「用語ごとに正解/不正解を集計した**実力**」（どの用語が弱いか）。
> `F-LOG-*` は「**いつ・何を・どう感じたか**という時系列の学習の軌跡」（続けられているか・振り返り）。
> 両者は同じ解答イベントから別の見せ方を作る（母 M-11 抽象化・§8）。「続けたくなる」動機設計の中心が LOG。

### Phase 1（MVP・最優先）— 4択クイズが毎日回せる

| ID | 機能 | 強さ | 概要 |
|---|---|---|---|
| F-TERM-01 | 用語データの読み込み | MUST | 静的JSONから用語を読み込む。`api/` 層経由（§8） |
| F-TERM-02 | 分野（カテゴリ）分類 | MUST | ネットワーク／セキュリティ／DB／開発手法 等で分類 |
| F-TERM-05 | 平易な説明（用語を用語で説明しない） | MUST | **未経験者向けの肝**。各用語に「中学生にも分かる」超平易な一言（`plainMeaning`）を持たせ、4択の解説・暗記カードで `meaning` と併記する。専門用語の連鎖（用語を用語で説明）を断つ（§4-5・§8） |
| F-QUIZ-01 | 4択出題 | MUST | 用語の意味を問う4択。選択肢はデータ駆動 |
| F-QUIZ-02 | 即時採点＋解説表示 | MUST | 正誤を即表示（ローカル判定）し、解説を出す（S軸） |
| F-QUIZ-03 | 選択肢の並び順ランダム化 | MUST | 正解位置を毎回散らす（学習メモ「正解位置ランダム化」継承） |
| F-QUIZ-04 | 分野別・ランダム出題の選択 | SHOULD | 分野を絞る／全分野ランダムを選べる |
| F-PROG-01 | 解答履歴の記録（localStorage） | MUST | 用語IDごとに正解/不正解を記録 |

### Phase 2 — 面接対策モード（本アプリの差別化の核）

| ID | 機能 | 強さ | 概要 |
|---|---|---|---|
| F-CARD-01 | 暗記カード（表=用語/裏=意味） | MUST | タップで裏返す。サクサク回す用途 |
| F-INTV-01 | 面接想定問答 | MUST | 「○○とは？」に対し**短い言い方（核の単語＋結論）**を表示。学習メモ「間を捨てる」継承 |
| F-INTV-02 | 自己採点（言えた/言えなかった） | SHOULD | 言えたかを自己申告し進捗へ反映 |

### Phase 2.5 — 面接対策の「コア」差別化（過去問道場に無い領域・§13）

> 「選べる」と「面接で言える」の間を埋める中核。未経験者は実体験で補えない分、ここを厚くする。

| ID | 機能 | 強さ | 概要 |
|---|---|---|---|
| F-TERM-04 | 実務シーン紐付け（現場での使われ方） | MUST | 各用語に「現場のどんな場面で出てくるか」の短いシーン（`scene`）を持たせる。未経験者が実装経験の代わりにイメージを得る（§13-1） |
| F-INTV-03 | 深掘り「なぜ?」チェーン | MUST | 1用語に2〜3段の追い質問（`followUps`）。例: TCP/IP正解→「UDPとの違いは?」→「どんな時UDP?」。面接特有の深掘り耐性を鍛える（§13-2） |
| F-INTV-04 | 模擬面接モード | SHOULD | 「質問→自分で声に出す/入力→模範解答と並べて自己評価」の1サイクル。任意でタイマー（結論を30秒で）（§13-3） |
| F-QUIZ-05 | 間隔反復（SRS）出題 | SHOULD | 苦手・未定着の用語を忘却曲線に沿って再出題（Leitner方式等の軽量実装）。`Progress` を入力に出題優先度を決める（§13-4） |

### Phase 3 — 進捗の可視化と弱点克服

|---|---|---|---|
| F-PROG-02 | 分野別正答率ダッシュボード | MUST | 分野ごとの正答率を可視化（S軸＝1画面で次の一手が分かる） |
| F-PROG-03 | 苦手用語の自動抽出・再出題 | SHOULD | 誤答の多い用語を優先出題する |
| F-PROG-04 | 進捗のリセット／エクスポート | SHOULD | localStorageの初期化・JSON書き出し（端末移行・バックアップ） |

#### 学習記録（ログ）— 続けたくなる動機設計の中心

| ID | 機能 | 強さ | 概要 |
|---|---|---|---|
| F-LOG-01 | 学習セッションの記録 | MUST | 1回の学習（日時・モード・出題数・正答数）を自動でログに残す。手入力不要で「つけ忘れ」を防ぐ |
| F-LOG-02 | 連続学習日数（ストリーク）・学習カレンダー | SHOULD | いつ学習したかをカレンダー／連続日数で可視化し、継続を動機づける（母 P-9 を満たす形で色のみに依存しない） |

|---|---|---|---|
| F-INTV-05 | 構造採点ルーブリック | SHOULD | 面接想定問答の自己採点を「言えた/言えない」の2値でなく「□結論から □理由 □具体例orトレードオフ」の3観点に。面接官が無意識に見る軸を可視化（§13-5） |

## 4. 非機能要件（母の品質4軸を継承して具体化）

各要件は母 第2部の要件IDを継承する。**本MVPで適用対象がないサーバー系MUSTは §逸脱記録 に集約**し、
ここでは本MVPで「適用対象がある」要件を具体化する。

### 4-1. 安定性・信頼性（母 S-*）

- **S-1（可用性）**：本MVPはSLAを**定めない**（静的ホスティング前提。母 S-1 の「定めないと明記する」に従う）。
- **localStorage 堅牢化**：読み込み時に JSON パース失敗・スキーマ不一致・容量超過を try/catch でガードし、
  壊れていれば**進捗のみ初期化して用語出題は継続**する（母 1-3 graceful degradation）。
- **データ整合性**：進捗カウンタはイベント発生時に同期更新し、表示時に集計し直して矛盾を補正（母 S-3 の精神）。

### 4-2. セキュリティ（母 SEC-*）— フロントで適用対象がある分のみ

- **SEC-5（XSS）**：用語・解説・面接文はプレーンテキストとして React の自動エスケープに委ねる。
  `dangerouslySetInnerHTML` を**使用禁止**。Markdown 等のHTML化を導入する場合のみ DOMPurify を必須化。
- **依存脆弱性**：`npm audit`（または dependency scan）を CI に常設し **High/Critical 0 件**を維持（母の精神）。
- **SEC-9（機密）**：本MVPは機密情報を持たない。将来サーバー化時に環境変数駆動を厳守（§逸脱記録）。

### 4-3. 保守性・拡張性（母 M-*）

- **M-1/M-2**：Issueファースト・PR経由・Conventional Commits（日本語）・main直push禁止（CLAUDE.md 準拠）。
- **M-3（責任分離）**：`api/`（データ取得）／`hooks/`（学習ロジック）／`components/`（表示）を分離。
  1ファイル肥大化を避ける。
- **M-4（エラー処理）**：データ読み込み・保存の失敗を一元ハンドリングし、silent catch しない。
- **M-11（抽象化＝交換可能）**：データ取得を `api/` 層に隔離し、localStorage 実装 ↔ サーバー実装を
  **1箇所の差し替え**で交換可能にする（本アプリの育つ設計の心臓部・§8）。
- **M-12（型安全）**：TypeScript を採用し、用語・進捗の型を定義する。
- **M-13（実ブラウザ検証）**：UIを伴う変更は実ブラウザで確認する（テスト緑≠UIが動く）。
- **M-6/M-7/M-8（CI・テスト）**：CI は lint→build→test の Fail Fast。テストはピラミッド型
  （ロジックの単体テスト中心。E2Eは主要導線のみ）。

### 4-4. 性能・UX（母 P-*）— ★S軸（突出）

- **P-1（性能目標）**：初回表示 < 1.5s／操作応答 < 100ms（ローカル判定）／Lighthouse Performance ≥ 90。
- **P-9（アクセシビリティ）**：**WCAG 2.1 Level AA 相当**（S軸のためAへ上乗せ）。label・alt・
  キーボードのみで全操作・色のみに依存しない正誤表示・コントラスト AA。
- **P-2（データ量）**：用語が増えても全件を一度に描画しない。出題は必要分のみ生成。
  将来サーバー化時はページネーション（母 P-2）へ。
- **P-8（楽観的UI）**：本MVPはローカル判定のため楽観的更新は不要（即時確定）。サーバー化時に検討。

### 4-5. 未経験者配慮（v0.3 追加・対象ユーザー §1-3 に対応）

> S軸（性能・UX）の一部として、未経験者が「圧倒されず・怖がらず・続けられる」ことを品質要件に格上げする。

- **平易な言葉ファースト（F-TERM-05＝MUST）**：説明文に未定義の専門用語を連鎖させない。
  専門語を使う場合は同じ画面で平易な言い換え（`plainMeaning`）を必ず添える。
  「用語を用語で説明して堂々巡り」を禁止する（未経験者が最も挫折する箇所）。
- **自信設計（続けられるUX）**：1問の操作を軽く保つ／正答時に小さな成功フィードバック／
  「今日やった量」を即可視化（F-LOG-02）。難しさより**達成感を先に**返す。
- **段階的開示**：1画面に情報を詰め込みすぎない。まず `plainMeaning` → 押すと `meaning` → さらに `scene`/`followUps`、
  と**ユーザーの準備に応じて深さを足す**（説明相手レベル切替 F-INTV-06 と接続）。
- **アクセシビリティ（P-9）はそのまま継承**：未経験者はスマホのスキマ時間利用が多い想定のため、モバイル最適化と
  キーボード/スクリーンリーダー対応の重要度がさらに上がる。

## 8. データモデル設計方針（本アプリ固有章）

> 母 §4-1 テンプレートの「アプリ固有の設計方針章」。本アプリの心臓部。

### 8-1. 1用語 → 3モードの導出

4択・暗記カード・面接問答は**別機能ではなく、1件の用語データの3つの見せ方**である（DRY）。

```ts
type Term = {
  // --- MVP（Phase 1）で使う中核フィールド ---
  id: string;            // 例 "tcp-ip"
  category: string;      // 例 "ネットワーク"
  term: string;          // 表示名 "TCP/IP"
  meaning: string;       // 正しい意味（暗記カード裏／4択の正解）
  distractors: string[]; // 誤答の選択肢（4択用。正解 meaning と混ぜて出題）
  interview: string;     // 面接での短い言い方（核の単語＋結論。学習メモ「間を捨てる」）

  // --- v0.3 追加：未経験者向け／面接対策の拡張（任意 = 後から段階的に埋める） ---
  plainMeaning?: string;            // 中学生にも分かる超平易な説明（F-TERM-05・未経験者MUSTの土台）
  scene?: string;                   // 現場での使われ方シーン（F-TERM-04・実装経験の代替イメージ）
  whyAsked?: string;                // なぜ面接で問われるか（学習の動機づけ）
  followUps?: { q: string; a: string }[]; // 深掘り「なぜ?」チェーン（F-INTV-03）
  reverseQuestions?: string[];      // この用語から派生する逆質問（F-INTV-07）
  related?: string[];               // 関連用語ID（知識マップ F-PROG-06）
  confusedWith?: string[];          // 混同しやすい用語ID（混同ペア分析 F-QUIZ-06）
};
```

> **拡張フィールドは全て任意（`?`）。** 既存12件（Phase1）は中核フィールドのみで動く。
> v0.3 の機能は用語データに列を足すだけで段階的に有効化でき、`api/` 隔離と同じく**作り直しゼロ**で育つ（母 M-11）。
> 未経験者向けの内容（`plainMeaning`/`scene`）は正確性レビュー（A-7）の対象を広げる点に注意（§10 R-01）。

- **4択** … `meaning` ＋ `distractors` を混ぜ、出題時にシャッフル（正解位置ランダム化）。解説に `plainMeaning` を併記（未経験者配慮）
- **暗記カード** … 表 `term` ／ 裏 `meaning`（＋ `plainMeaning`）
- **面接問答** … 問「`term` とは？」／模範 `interview`／深掘り `followUps`

### 8-2. 進捗データは別レイヤ（用語IDで紐付け）

```ts
type Progress = {
  [termId: string]: { correct: number; wrong: number; lastAnsweredAt: string };
};
```

進捗は用語データと分離し、`termId` で結合する。これにより用語の追加・修正が進捗を壊さない。

### 8-3. 学習記録（ログ）も別レイヤ（時系列の軌跡）

`Progress`（用語ごとの実力）とは別に、`LearningLog`（いつ・何を・どう感じたか）を時系列で持つ（F-LOG-*）。

```ts
type LearningSession = {
  id: string;            // セッションID
  startedAt: string;     // 学習日時（ISO）
  mode: "quiz" | "card" | "interview";
  asked: number;         // 出題数
  correct: number;       // 正答数（card/interview は「言えた」数）
};

type LearningNote = {
  id: string;
  createdAt: string;
  termId?: string;       // 用語に紐付く場合（任意）
  body: string;          // 気づき・面接で詰まった点（プレーンテキスト＝XSS非該当）
};

type LearningLog = {
  sessions: LearningSession[];
  notes: LearningNote[];
};
```

- **ストリーク／カレンダー**（F-LOG-02）は `sessions[].startedAt` を日付集計して導出（保存はせず表示時計算＝母 P-4 の精神）。
- `Progress` と `LearningLog` は**同じ解答イベント**から更新されるが、見せ方が違う（実力 vs 軌跡）。

### 8-4. `api/` 層の隔離（育つ設計の核）

画面・フックは「データがどこから来るか」を知らない。`api/` のインタフェースだけに依存する。

```ts
// api/termRepository.ts（インタフェース）
getTerms(): Promise<Term[]>;
getProgress(): Promise<Progress>;
saveProgress(p: Progress): Promise<void>;
getLearningLog(): Promise<LearningLog>;        // F-LOG
saveLearningLog(log: LearningLog): Promise<void>;
```

- **MVP**：`localStorageTermRepository`（JSON同梱＋localStorage）
- **Phase 4**：`httpTermRepository`（Spring Boot 等のサーバーAPI）に**差し替えるだけ**で画面は無改修。

→ 母 M-11（抽象化で交換可能）の実践。これが「今は軽く・あとで多人数化」を作り直しゼロで両立させる。

## 10. リスク・前提（R-* 形式）

| ID | リスク | 対策 |

## 11. 逸脱記録（母 §4-5・MUST不適用の棚卸し）

> 母の MUST のうち、本MVP（静的SPA・認証/DB/サーバーなし）で**適用対象がない**ものを明示する。
> これらは「未達（床割れ）」ではなく「適用対象なし（N/A）」であり、**Phase 4 多人数化で有効化**する。
> §8-3 の `api/` 隔離により、有効化は作り直しなしで可能。

| 母要件 | 内容 | 本MVPでの扱い | 有効化フェーズ |

## 13. 面接対策機能の詳細（v0.3 新設・過去問道場に無い差別化領域）

> **設計の中心思想:** 過去問道場は「**選べる**（4択正答率）」を鍛える。本アプリは未経験者を対象に
> 「**面接で言える**」まで運ぶ。両者の間にあるギャップ（言語化・深掘り耐性・実務イメージ・表現の構造）を
> 機能で埋めるのが本章。各機能は「面接官が実際に何を見ているか」から逆算して定義する。
>
> **未経験者という前提が効く点:** 経験者なら実務エピソードで補える部分を、未経験者は補えない。
> だからこそ §13-1（実務シーン）と §13-3（模擬面接）でイメージと場数を、§13-2（深掘り）で"なぜ"への耐性を、
> アプリ側が肩代わりする。

### 面接官が見ている軸 → 対応機能（対応表）

| 面接官が無意識に見ている軸 | 過去問道場 | 本アプリの対応機能 |
|---|---|---|
| 用語を自分の言葉で言えるか | ✗ | F-INTV-01/04（面接問答・模擬面接） |
| 知識が実務に結びつくイメージがあるか | ✗ | F-TERM-04（実務シーン） |
| 「なぜ?」の深掘りに耐えられるか | ✗ | F-INTV-03（深掘りチェーン） |
| 構造立てて話せるか（結論→理由→具体） | ✗ | F-INTV-05（構造採点ルーブリック） |
| 相手に合わせて説明を変えられるか | ✗ | F-INTV-06（説明相手レベル切替） |
| 紛らわしい概念を区別できているか | △（解説のみ） | F-QUIZ-06（混同ペア分析） |
| 概念どうしの関係を俯瞰できているか | ✗ | F-PROG-06（知識マップ） |
| 人物面（志望動機・困難の乗り越え） | ✗ | F-BHV-01（行動面接STAR） |
| 逆質問で意欲・理解度を示せるか | ✗ | F-INTV-07（逆質問ストック） |
| 苦手を効率よく潰しているか | △（苦手復習） | F-QUIZ-05（間隔反復SRS） |

### コア機能（Phase 2.5）

#### 13-1. 実務シーン紐付け（F-TERM-04）
各用語に「現場のどんな場面で出てくるか」の短いシーンを `scene` で持たせる。
未経験者は実装経験が無いため、これが**経験の代替イメージ**になる。
例：`CI/CD` → 「コードをpushすると自動でテストが走り、問題なければ本番に反映される。毎日何度もデプロイする現場で使う」。
面接で「使ったことは?」と聞かれても、最低限"どんな場面の技術か"を語れる状態にする。

#### 13-2. 深掘り「なぜ?」チェーン（F-INTV-03）
1用語に2〜3段の追い質問を `followUps`（`{q, a}[]`）で持たせる。面接は1問1答で終わらず必ず重ねてくる。
例：`TCP/IP` 正解 → 「UDPとの違いは?」→「どんな時にUDPを使う?（動画・ゲーム等）」。
**1段の暗記**から**連鎖した理解**へ引き上げる。未経験者が最も崩れる「なぜ?」に的を絞る。

#### 13-3. 模擬面接モード（F-INTV-04）
「質問を出す → ユーザーが声に出す/入力する → 模範解答(`interview`)と並べて自己評価」の1サイクル。
任意でタイマー（結論を30秒で言う練習）。**場数**を踏ませ、本番の緊張に近い状況を作る。

#### 13-4. 間隔反復（SRS・F-QUIZ-05）
`Progress`（正誤集計）を入力に、苦手・未定着の用語を忘却曲線に沿って再出題する（Leitner方式等の軽量実装）。
過去問道場の「苦手復習」より科学的で、限られた転職準備期間を効率化する。

### 差別化機能（Phase 3）

#### 13-5. 構造採点ルーブリック（F-INTV-05）
自己採点を「言えた/言えない」の2値でなく **□結論から □理由 □具体例orトレードオフ** の3観点に分解。
面接官が無意識に評価している「話の構造」を可視化し、反復で身につける。

#### 13-6. 説明相手レベル切替（F-INTV-06）
同じ用語を「**完全初心者向け**（`plainMeaning`）／面接官向け（`meaning`+`interview`）」で切り替え表示。
面接の「分かりやすく説明して」への対策。未経験者向けに作った `plainMeaning`(F-TERM-05) をそのまま再利用できる。

#### 13-7. 逆質問ストック（F-INTV-07）
用語に紐づく逆質問を `reverseQuestions` で貯める。例：`CI/CD` →「御社のデプロイ頻度とロールバック体制は?」。
面接終盤の「何か質問は?」は評価対象。未経験者でも"理解の深さ"を示せる武器にする。

#### 13-8. 混同ペア分析（F-QUIZ-06）
どの誤答(distractor)に引っかかったかを記録し、紛らわしい用語ペア（`confusedWith`）を対比学習に回す。
例：アジャイル↔ウォーターフォール、公開鍵↔共通鍵。**間違え方**から弱点を特定する。

#### 13-9. 知識マップ（F-PROG-06・MAY）
用語どうしのつながり（`related`）を可視化。例：TCP/IP—DNS—HTTPS。
点の暗記でなく**面の理解**を促し、面接で"systems thinking"を語る材料にする。

#### 13-10. 行動面接（STAR）練習（F-BHV-01・MAY）
技術用語と別に、未経験者が**必ず**聞かれる人物質問（「なぜIT業界?」「未経験だが大丈夫か」「困難をどう乗り越えたか」）を
STAR法（Situation/Task/Action/Result）の型で練習する。技術と人物の両輪で面接全体をカバーする。

> **実装の段取り（推奨）:** まず未経験者の土台 F-TERM-05（平易説明）→ F-TERM-04（実務シーン）を用語データに足し、
> 次に F-INTV-03（深掘り）→ F-QUIZ-05（SRS）→ F-INTV-04（模擬面接）の順。表現力系（13-5〜13-7）と
> 俯瞰系（13-8〜13-10）は用語データが充実してから。すべて `Term` への列追加で段階導入でき、画面は `api/` 隔離のまま育つ。

## 14. ユーザー作問・共有（F-USER・v0.4）

> **狙い:** 転職に成功したエンジニア（経験者＝講師役）が「**実際に聞かれた面接質問**」や用語を自分で書き、
> 他の学習者に配れるようにする。未経験者は「現場のリアルな質問」で練習でき、知見が循環する。

### 14-1. 設計方針（静的SPAの維持）
- 要件定義書 §1-5 の方針どおり**サーバー・認証・DBを持たない**。作問データは各自の localStorage に保存。
- **共有はエクスポート/インポート**（サーバー無しのピア共有）。`UserContent` を base64 の「共有コード」に
  して Discord 等に貼り、受け取った人が取り込む。多人数化（Phase 4）に踏み込まず「共有」を実現する。

### 14-2. 機能
| ID | 機能 | 内容 |
|---|---|---|
| F-USER-01 | 作問 | **4択用語**（term/意味/誤答3/面接の言い方/平易）と**面接Q&A**（質問/模範回答/分野/メモ）を作成・一覧・削除 |
| F-USER-02 | エクスポート/インポート | 作問データを共有コード化して書き出し／貼り付けて取り込み（IDは取り込み時に振り直し衝突回避） |
| F-INTV-01 | 面接練習（併せて実装） | 同梱用語の `interview`＋ユーザー作問の面接Q&A を「質問→模範回答」で練習 |

### 14-3. データ・画面
- 型：`Term.source`（builtin/user）／`InterviewQuestion`／`UserContent`（§8・データモデル.md）。
- 画面：ヘッダーのモード切替ナビ（4択クイズ／面接練習／マイ問題）。マイ問題はサブタブ（面接Q&A／4択用語／共有）。
- `getTerms()` が builtin＋user を統合するため、作問した4択用語は即クイズに反映される（`api/` 隔離は維持）。

### 14-4. 品質・安全
- 作問データ破損時は空で返し、同梱用語の出題は継続（A-4 graceful degradation）。
- 入力はプレーンテキストとして React の自動エスケープに委ねる（SEC-5・`dangerouslySetInnerHTML` 不使用）。
- 全画面で Lighthouse Accessibility=100 を維持（フォームはラベル付与・見出し階層を整備）。

> **注意（将来）:** インポートは他者由来のデータを取り込むため、サーバー共有（Phase 4）へ拡張する際は
> 内容の検証・モデレーション・サイズ制限を設計する（現状はローカル取り込みのみで攻撃面は限定的）。

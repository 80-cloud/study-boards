## 第0部：このドキュメントの位置づけ（メタ章）

### 0-1. 本書の目的

個別アプリの要件定義書（子）を作るたびに、毎回ゼロから安定性・セキュリティ・保守性・性能の要件を考え直すのは非効率であり、抜け漏れ（＝短所）の温床になる。本書は、**どのアプリでも共通して満たすべき要件と、その背後にある設計判断基準（なぜそうするか）**を一度だけ定義し、子に継承させる原典である。

### 0-2. 親子関係のルール

```
母要件定義書（本書 ＝ 原典）
   │  継承（子は本書の全要件を満たす）
   ├── アプリA 要件定義書（特化）
   ├── アプリB 要件定義書（特化）
   └── アプリC 要件定義書（特化）
         │  Standardize（S）の逆流
         └──→ 子で得た普遍的知見を本書へ昇格させる
```

- 子は本書を**継承**する。本書の品質4軸（第2部）と横断要件（第3部）は、子で「対象外」にできない（学習用などで簡素化する場合も、簡素化した事実と理由を子に明記する）。
- 子は**特化部分のみ追記**する：そのアプリ固有の機能・ドメイン・性能目標・UX。
- 子の記述が本書と矛盾する場合は、§4-5 の逸脱ルールに従い承認をはさむ。
- 子で発見した普遍的な知見（事故・改善・標準化）は、§4-3 の S（標準化）で本書へ逆流させる。

### 0-3. 設計思想：母はオールA（床）、子はA床＋選択的S

本書（母）と子の品質には、明確な役割分担がある。

| | 母（本書） | 子（各アプリ） |
|---|---|---|
| 役割 | 守りの土台 | 攻めの突出 |
| 品質 | **オールA＝全軸が A 以上（弱点ゼロ）** | **A床を継承＋品質4軸のうち1〜2軸を S へ** |
| 強み | 短所がないこと | A床の安心の上に立つ、突出した長所 |
| 狙い | どのアプリも壊れない床を継承させる | そのアプリの目玉（差別化）で尖る |

**なぜ母はオールAなのか（オールSを母にしない理由）：** 全軸を同時にSで狙うと、ある軸を尖らせる代償に別の軸が必ず犠牲になり、**床（A）が割れて弱点が生まれる**。母が弱点を持つと、それを全ての子が継承してしまう。だから母は突出を捨て、弱点ゼロの床に徹する。

**なぜ子はSを取れるのか：** 母がオールAの床を保証しているからこそ、子は1〜2軸をSへ引き上げても他軸がA未満に落ちない。**床があるから安全に尖れる。** これが「丸ごとオールS狙い（床を割る）」との決定的な違いである。

#### Sの鉄則（子が守ること）

1. **S化は品質4軸のうち1〜2軸まで**（安定性・信頼性 / セキュリティ / 保守性・拡張性 / 性能・UX のいずれか）。欲張って全軸Sを狙わない。
2. **Sを取るために、他のどの軸も A 未満に落とさない**（床を割らない）。割りそうなら、そのSは諦めるか設計し直す。
3. 子は「どの軸をSにするか」と「その代償に何をA未満に落とさないと約束するか」を**S軸宣言**（§4-1 第0項）に明記する。
4. Sは A の上位指標で測る（付録A の S判定欄）。「A（弱点なし）」を満たして初めて S を名乗れる。

> **大前提は安定性**である。様々なアプリが正常動作すること（§1-1 で定義）を、機能の華やかさより常に優先する。
> 「便利さ」と「安全性」がトレードオフになる局面では、**安全性（＝床を割らないこと）を採る**（CLAUDE.md §13 の教訓と一致）。
> 技術選定も同様に「最強の技術」でなく「プロジェクトに合う・弱点が少ない技術」を選ぶ（B-Q36・A-Q35）。
>
> **既存アプリの暗黙のS（例）：** slack-board＝性能・UX軸（リアルタイム通信）／ sns-board＝性能・UX軸（タイムラインUX）／ TripDiary＝性能・UX＋機能厚（凝ったアプリ）／ task-board＝あえて尖らせず全軸A（堅実なCRUD土台）。母はこれを「宣言」として明文化する。

### 0-4. 用語・記法

- 要件の強さは **MUST（必須）／ SHOULD（推奨）／ MAY（任意）** で表す。
- 品質4軸を貫く要件は本書（親）が MUST を定める。子は MUST を緩められない。
- 要件IDの採番規則は付録C。
- 本書内の `B-Qn`（基礎編）/ `A-Qn`（上級編）は設計判断カード（付録B）の設問番号を指し、各要件の「Why（判断根拠）」へのポインタとして用いる。
- **`§` 記法はセクション番号の略記であり、GitHub Markdown のアンカーリンクではない（クリック不可）。** 該当番号の見出しを参照すること。アンカーリンク化は付録D の TODO で予定。
- 本書自身の配置パスは `docs/母要件定義書.md`（リポジトリルート直下）。子から本書を参照する際はこのパスを基準にする。

## 第1部：絶対的前提（不変条件）

どのアプリに展開しても崩してはならない大前提。すべての子が無条件に継承する。

### 1-1. 安定性の定義（「正常動作する」とは何か）

「安定して正常動作する」を、測定可能な言葉で定義する。子はこの定義を自アプリの数値目標に具体化する（第2部）。

| 観点 | 「正常動作」の定義 |
|---|---|
| 機能正当性 | 仕様どおりの結果を返す（受入条件・境界値で検証可能：B-Q29） |
| データ整合性 | 障害・並行操作・再試行があってもデータが矛盾しない |
| 障害耐性 | 一部が壊れても全体が止まらない（graceful degradation） |
| 回復性 | 壊れても復旧手順が定義され、データ損失が許容範囲に収まる |
| 予測可能性 | 同じ入力に同じ結果。flaky（不安定）でない（A-Q23） |

### 1-2. 非機能を機能より優先する原則

- 機能要件（何ができるか）より、非機能要件（安全に・壊れず・直しやすく動くか）を優先する。
- 新機能の追加が品質4軸のいずれかを A 未満に下げるなら、その機能は MUST ではなく SHOULD/MAY に格下げするか、4軸を保てる設計に作り直す。

### 1-3. 失敗の許容範囲（壊れ方の設計）

「壊れないこと」だけでなく **「どう壊れるか」** を設計する。

- 揮発的・非本質的なデータ（入力中表示・一時通知など）は、障害時に**割り切って捨ててよい**（A-Q3）。
- 本質的なデータ（メッセージ・投稿・取引）は、**欠落させず後から補完できる**設計にする（再接続後の差分取得 `?since=` 等：A-Q3）。
- 不可逆操作（削除・上書き・本番への破壊的変更）は、**人間の承認をはさむまで実行されない**ことをデフォルトにする（A-Q28・CLAUDE.md §12）。

## 第2部：品質4軸の標準要件（オールAの中身）

子が必ず満たすべき共通要件。各軸は「測れる基準」と「Why（判断根拠）」をセットで持つ。子はここに自アプリ固有の数値・対象を肉付けする。

### 2-1. 安定性・信頼性

| # | 要件 | 強さ | Why（根拠） |
|---|---|---|---|
| S-1 | 可用性目標（SLA/メンテ方針）を子で定義する | MUST | 学習用は SLA 任意でよいが「定めない」と明記する |
| S-2 | 冗長化（壊れても止まらない）とスケーリング（負荷に耐える）を区別して設計する | MUST | 目的が異なる。混同が過剰/過小設計を生む（A-Q17・A-Q23(AWS ALB)） |
| S-3 | データ整合性は非正規化カウンタを同一トランザクションで更新し、定期再計算バッチでズレを補正する | MUST | counter_cache はズレる前提で再計算を持つ（A-Q8・全4本共通） |
| S-4 | 削除は原則ソフトデリート（論理削除）。参照整合性・履歴を保つ | SHOULD | 物理削除は孤児・カウンタ不整合を生む。容量はpurgeバッチで管理（A-Q31） |
| S-5 | DB変更は Flyway 等でコード管理（追跡可能・実行順保証）。本番マイグレーションは Append-only・Expand/Contract で後方互換を保ち、破壊的変更を分割する | MUST | 直接ALTERは追跡不能（B-Q14）。新旧同時稼働で旧が壊れる（A-Q28） |
| S-6 | 不可逆操作（DROP/TRUNCATE/destroy 等）の前にバックアップ＋人間承認をはさむ | MUST | AI単独completion禁止（A-Q28・CLAUDE.md §12） |
| S-7 | デプロイはゼロダウンタイム（ローリング100%/200%・コネクションドレイン）を志向する | SHOULD | 入れ替えの空白・処理中リクエストを守る（A-Q27） |
| S-8 | 接続維持系の機能は切断検知・自動再接続（指数バックオフ）・再購読・欠落補完を持つ | SHOULD | 不安定回線でも自然に使える（A-Q3） |

### 2-2. セキュリティ

既存4本の §4-2 セキュリティ表がほぼ完成形のため、本書はそれを親の MUST 群として昇格させる。

| # | 要件 | 強さ | Why（根拠） |
|---|---|---|---|
| SEC-1 | パスワードは bcrypt（コスト10以上）等の適応的ハッシュ（不可逆）で保存 | MUST | 平文・可逆暗号は厳禁。漏洩時の被害を減らす（B-Q3・全4本共通） |
| SEC-2 | 認可は必ずバックエンドで行う。フロントの制御はUX補助に過ぎない | MUST | 鍵をかけずに貼り紙だけの状態を作らない。IDOR対策（B-Q4・A-Q33） |
| SEC-3 | 親子IDエンドポイントは子の所有（parentId一致）を検証し、不一致は404 | MUST | URL書き換えで他人の資源が見える事故を防ぐ（A-Q33） |
| SEC-4 | 権限はロールベース。「誰か」でなく「この場で何の権限を持つか」で判定 | MUST | moderator等の将来追加に耐える（A-Q34） |
| SEC-5 | XSS対策：プレーンテキストはフレームワークの自動エスケープ。HTML化（Markdown等）は変換→DOMPurify除去→URL/タグ制限→CSPの多層防御。安全確認なき `dangerouslySetInnerHTML` 禁止 | MUST | Reactでも油断は危険。HTML化する以上XSSは必ず起こりうる（B-Q7・A-Q12） |
| SEC-6 | SQLインジェクション：ORM/Prepared Statement・バインド（`#{}`）必須、文字列結合（`${}`）はホワイトリスト検証時のみ | MUST | 文字列結合は注入を招く（B-Q6・全4本共通） |
| SEC-7 | 認証セッションは盗難耐性のある方式（例：JWT in HttpOnly Cookie、access短命+refresh DB rotation+reuse detection）。401時はインターセプターで refresh→再試行を一元化 | MUST | XSSでのトークン窃取耐性（B-Q1/Q2/Q15・slack/sns で標準化済み） |
| SEC-8 | ファイルアップロードは中身（マジックバイト）で判定し、拡張子・Content-Typeを信用しない。サイズ/再生時間で上限。保存は外部（S3等）に隔離 | MUST | 最も攻撃面が広い。拡張子・MIMEは詐称できる（A-Q13・B-Q34） |
| SEC-9 | 機密情報は環境変数/シークレットストア駆動。設定ファイルへの平文記載・コミット禁止 | MUST | 削除してもPR/Forkに残る。task-board 2026-05-07 事故の継承（B-Q25・CLAUDE.md §6・§13） |

| SEC-11 | CORSは自身が運用するオリジンのみ許可（ワイルドカード回避） | MUST | 任意サイトからのAPI悪用を防ぐ（B-Q5・CLAUDE.md §10） |

|---|---|---|---|

### 2-4. 性能・UX

| # | 要件 | 強さ | Why（根拠） |
|---|---|---|---|
| P-1 | 主要操作にパフォーマンス目標値（API応答・初回表示・アップロード）を子で定義 | MUST | 全4本 §4-1 が目標値表の型 |
| P-2 | 大量・増加し続けるデータは全件取得しない。ページネーション（小規模=Offset / 大量=Cursor）＋最新N件 | MUST | 全件取得はDB負荷・転送量・初期表示が破綻（B-Q33・A-Q31） |
| P-3 | N+1問題を避ける（JOIN FETCH / EntityGraph）。ORM利用時は特に検出する | MUST | 件数分の追加クエリで線形に遅延（B-Q32） |

| P-6 | コネクションプールは過大設定しない。常時接続（WS等）と短命DB接続を混同しない | MUST | 過大プールはDBを圧迫・枯渇させる（A-Q16） |

## 第3部：横断要件（4軸を貫く共通ルール）

### 3-1. ログ・監視・オブザーバビリティ

- 監視（既知の問題を見張る）とオブザーバビリティ（未知も後から調査できる）を区別する（A-Q29）。
- 4ゴールデンシグナル（Latency / Traffic / Errors / Saturation）を基本とする（A-Q29）。
- ログは構造化（機械解析可能）し、requestId / userId を MDC で自動付与して追跡性を上げる（B-Q26）。
- リアルタイム機能を持つアプリは、接続数・切断数・再接続数・配信遅延も監視する（A-Q29）。
- アラートは「鳴らして終わり」にせず、重大度判定→Runbook（対処手順）→復旧まで定義する（A-Q29）。

### 3-2. 設定・機密情報の外部化

- 機密情報は環境変数 / シークレットストア駆動。コードにハードコードしない（SEC-9）。環境変数でも漏洩リスクはゼロでない点に留意（B-Q25）。
- 環境固有値（IP・エンドポイント・バケット名）は外部化し、プロファイルで切替える（CLAUDE.md §12-4・B-Q13）。

### 3-3. エラーハンドリング標準

- silent catch（握り潰し）禁止。例外はグローバル例外ハンドラ等で一元処理し、形式を統一する（B-Q11）。
- batchロード結果・外部取得結果は null ガードする。
- 永続化はダーティチェック依存でなく明示 save() を行う。
- 新エンティティは生成時刻等の自動設定（@PrePersist 等）を持ち、実際に永続化する統合テストで検証する（mockは初期化漏れを見逃す）。

### 3-4. リリース・運用フロー（誤操作の多層防御）

- GitHub Flow（main中心・小〜中規模Web向け）を基本とする（A-Q21）。
- 変更は Issue→ブランチ→PR→セルフレビュー→CI緑→マージ（CLAUDE.md）。
- AI単独で完結させない操作（destroy / 本番削除 / 破壊的SQL）は人間承認をはさむ（CLAUDE.md §12-2、A-Q28）。
- 障害対応は §4-3 の C→A→S（PDCAS）として運用する。

### 4-1. 派生テンプレート（子ドキュメントのひな形）

> **第0項「オールA宣言 ＋ S軸宣言」**は、子の作成者が継承の意図とSの狙いを意識的に確認するための欄。以下を明記する（§0-3 のSの鉄則に従う）：
> - **継承宣言**：「本書（母要件定義書 vX.Y）を継承し、品質4軸すべてを A 以上（床）に保つ」
> - **S軸宣言**：S化する1〜2軸と、その突出内容を**測定可能なS基準（数値・合否条件）で書く**。「速い」「拡張しやすい」のような形容詞で終わらせない（例：◯「性能・UX軸をSへ＝WebSocket配信レイテンシ p95 < 200ms を負荷試験で実証」／✕「リアルタイムを頑張る」）。S基準は付録A S判定表に転記し、C（評価）で測る。
> - **床を割らない約束**：Sを取る代償に A 未満へ落とさないと約束する軸（例：「Sのためにセキュリティ・安定性をA未満にしない。WS認証・再接続・順序保証はA基準を満たす」）
> - **`S-` 接頭辞の扱い**（付録C 注記。安定性要件 `S-` と画面ID `S-01` の区別）
>
> 「差別化ポイント」表（本家 vs 自作で機能を意図的に削る判断）は、オールA思想「不要を切って短所を作らない」と直結するため、子でも必ず書く。
>
> **改訂履歴の版表記：** 子は「版 0.1, 0.2, 1.0」形式（本書と同じ）に揃える。task-board は旧「バージョン 1.0」形式だが、新規・改訂時は本形式へ統一する（混在を避けるための横断方針）。

### 4-2. 継承チェックリスト（親の4軸を満たしたか）

子は実装着手前と提出前に、付録Aの **A判定表（床）で第2部の全MUST要件**を満たしているか、**S判定表で宣言したS軸**が上位指標に達したかを確認する。簡素化する場合は「簡素化した事実・理由・本格運用時の論点」を子に明記する（既存4本の §4-3 法令注記・§5 対象外の書き方を踏襲）。

### 4-3. トヨタ式PDCAS運用サイクル

子ドキュメントは PDCAS で運用・改善する。トヨタ式の肝は最後の **S（標準化）** であり、改善を個人の手柄で終わらせず「標準」に固定し、次の Plan の土台にする。

| 段階 | 子で行うこと | 本書との対応 |
|---|---|---|
| **P** lan | 親（本書）を継承し、アプリ固有要件を計画する（4-1テンプレ＋4軸具体化） | 第2部の数値化 |
| **D** o | 実装・展開する（Issue→PR→CI→デプロイ） | 第3部 §3-4 |
| **C** heck | 品質4軸で評価する（付録A判定表・受入条件・境界値テスト・パフォーマンステスト・実ブラウザ検証） | 第2部・M-13 |
| **A** ct | なぜなぜ分析で根本原因まで掘って改善する（症状と原因を分離・「誰が悪いか」でなく「なぜ防げなかったか」） | §4-4・A-Q32 |

#### C→A の具体手順（障害対応＝なぜなぜ分析、A-Q32）

```
① 異常検知 → ② 影響確認・切り分け → ③ 一次対応（止血）
   → ④ 原因特定（RCA：症状と原因を分離・再現） → ⑤ 根本修正 → ⑥ 再発防止
```

再発防止は表で残す（問題→対策。例：危険デプロイ→CI追加 / N+1見逃し→自動テスト / DB削除事故→承認制 / 手順ミス→Runbook化）。

### 4-4. S（標準化）：母への逆流手順

本書の最大の付加価値。子で得た普遍的知見を親へ昇格させる閉ループを明文化する。

**逆流の判定基準（昇格すべきか）：**
- そのアプリ固有でなく、**他のアプリでも再発・適用しうる**知見か。
- 事故・脆弱性・性能問題の**根本原因と対策**がセットになっているか。

**手順：**
1. 子の C→A で得た知見を、子の「リスク・前提」表または再発防止表に記録する。
2. 上記の判定基準を満たすなら、本書（母）に対して Issue を立てる（CLAUDE.md §11 本書更新ルール）。
3. PR経由で本書の第1〜3部（要件）または付録（判断カード）へ昇格させる。
4. 既存の子にも遡って反映すべきか判断する。

**逆流の実例（既に起きている標準化）：**
- 「task-board 2026-05-07 機密情報事故」→ 全4本が §2制約・§4セキュリティ（SEC-9）へ継承。
- 「他組織の Terraform 本番全削除事故」（CLAUDE.md §13-1）→ 本書 S-6（不可逆操作前のバックアップ＋人間承認）・§3-4（AI単独で完結させない）・RDS の `lifecycle.prevent_destroy` へ直結。**事故 → S逆流 → 多層防御の要件化**が連鎖した実例。
- slack-board が sns-board の認証文言（JWT 2段方式）を継承、TripDiary が recipe/sns を継承。
- これらは暗黙の慣習だった。本書はこれを **PDCAS の S：正式手順**として明文化する。

### 4-5. 逸脱ルール

子がやむを得ず本書の MUST に反する場合：
1. 反する要件IDと理由を子に明記する。
2. 本書に対し Issue を立て、人間の承認をはさむ。
3. 承認後、子に「親要件 X を Y の理由で逸脱」と記録する。学習用での簡素化もこの記録対象とする。

### 付録C. 要件ID採番規則

- 親（本書）の品質要件：軸の頭文字＋連番（`S-` 安定性 / `SEC-` セキュリティ / `M-` 保守性 / `P-` 性能UX）。
- 設計判断カード：`B-Qn`（基礎編）/ `A-Qn`（上級編）。
- 子の機能要件：`F-<ドメイン>-<連番>`（例 `F-AUTH-01`、既存4本の慣習を踏襲）。
- 子の画面：`S-<連番>`（例 `S-01`）、リスク：`R-<連番>`。

> **`S-` の衝突注意:** 本書の安定性要件 `S-1` と、子の画面ID `S-01` は接頭辞が重なる。ゼロパディング有無で区別できるが、横断参照では混乱しうる。子テンプレートの冒頭に「本書の `S-` は安定性要件の親ID、画面要件は `S-01` 形式（または `SCR-` を採用）」と一言注記すること。新規アプリでは画面に `SCR-` を採用してもよい（既存4本は `S-` 慣習を踏襲）。
